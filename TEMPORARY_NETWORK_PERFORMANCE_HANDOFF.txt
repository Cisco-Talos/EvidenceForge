Prompt for the continuing agent
-------------------------------

Continue the EvidenceForge long-scenario network-generation performance effort on
`codex/fix-dns-watermark-order`. The user observed a roughly 55-minute warm-up for a long scenario
and later found that v2.0.0 remained slower than v1.17.0. We used py-spy to establish that this was
not the old duration-growing cache-search problem. Instead, trusted engine-owned objects were paying
for defenses against malicious Python already executing inside the process.

The approved threat model is now:

* Scenario/configuration/pack/raw-payload inputs remain untrusted and must be structurally validated
  and detached at their boundary.
* Exact canonical objects created and exchanged inside the generation engine are trusted.
* Do not retain or reintroduce defenses against monkeypatching, object.__setattr__, hostile callbacks,
  malicious repr/equality/hash/copy methods, code replacement, or arbitrary in-process mutation.
* Preserve manager ownership, exact retained-capability identity, active/generation/version/counter
  fences, stale-handle and double-finalization rejection, RNG drift detection, atomic commit/cancel,
  rollback, lost-return reconciliation, retry, deterministic output, filesystem safety, external
  validation, and persistent spool corruption detection.
* Do not change scenarios, schemas, the CLI, output formats, RNG consumption, timestamps, identifiers,
  ordering, serialization, or supported public APIs.

Profiling findings
------------------

The last Stage-4 60-second py-spy capture contained about 5,995 samples. The former dominant stacks
were gone: recursive RNG-state validation, per-call cursor graph preflight, HMAC graph authentication,
and class/function/closure authentication no longer dominated. Residual inclusive costs were roughly:

* trusted request stable-ID encoding: 667 samples (~11 percent)
* prepared SourceTimingPlanner work: 612 samples (~10 percent)
* deepcopy: roughly 500 samples (~8-10 percent)
* SourceTimingPlanner.state_digest: 216 samples (~3.6 percent)

The 66e2166d follow-up directly targets these residual costs, but it has not yet had a matched py-spy
capture or completed shortened-scenario performance/parity run. The raw profiles were intentionally
