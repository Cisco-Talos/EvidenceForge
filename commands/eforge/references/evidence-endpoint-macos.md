# macOS workstation evidence

This branch is implementing macOS 26 arm64 workstation evidence. Running EvidenceForge or Studio on a Mac is a separate capability. The foundation and bounded history profile are experimental; complete Mac-native investigation coverage is not yet available.

Use existing `environment.systems` values: `os: macOS 26`, explicit `os_build`, `architecture: arm64`, `type: workstation`, user placement, roles/services and software deployment. Use existing source deployment, collection, observation/timing and application overlay semantics. There is no parallel Mac configuration block. Preserve older scenarios and published packs; add new pack versions for changed defaults.

Select eCAR for modeled endpoint process/session/flow evidence. Existing network, firewall, IDS, proxy, mail and server evidence can describe Mac interactions only when routing and sensor visibility permit it. Windows Security/Sysmon and Linux syslog remain local to their actual owners. Native Mac `logind` is not Linux `systemd-logind`.

`zsh_history` writes `<host>/zsh_history/<username>.zsh_history` as `: epoch:0;command`. Its initial collection profile models EXTENDED_HISTORY with incremental append at interactive command submission; zero duration is not measured execution time. Only a live, explicitly interactive `/bin/zsh` shell in the owning session can submit history. Process creation alone does not imply history. Mac Bash uses the existing `bash_history` format only for an explicitly modeled interactive `/bin/bash` session. Noninteractive commands, multiline/metafied zsh records, history erasure and delayed session-exit history persistence remain outside this profile. [zsh history options](https://zsh.sourceforge.io/Doc/Release/Options.html#History) describe the native semantics.

Application availability and implemented variants are distinct. Unresolved Mac variants are unavailable rather than substituted with Linux/Windows paths. Initial managed variants have a conservative 2026-10-15 catalog-snapshot availability floor; host-bundled entries follow the modeled OS build. Paths and command pools come from catalog data, never the generator host or personal inventories. Chrome’s profiled renderer/GPU/utility helpers use existing application `children` and spawn-rule fields. The GUI baseline binds a modeled subset to the installed browser and owning session; counts/delays are synthetic profile values. Release overrides must also update versioned helper paths. Browser IPC and helper-attributed network traffic are not inferred.

Optional application-platform `code_signature` records explicit main-executable `signing_id` and optional/null `team_id`; existing architecture/deployment fields still apply. Unknown signing metadata stays absent, and helpers do not inherit their owner's signer. CodeDirectory hashes are independently modeled per release/architecture, separate from content hashes. Optional `executable_format: mach_o` independently identifies a known main image under the existing explicit arm64 deployment; it derives a synthetic release-scoped UUID without inferring format from signing or paths. Missing format stays unknown and helpers do not inherit image metadata. The native audit PID version is owned by process state across creation, exec and checkpoint recovery; it is not the PID or execution ordinal. These foundations do not establish complete native ES process metadata or trust-policy outcomes.

Mac-local file populations use existing `environment.storage.file_sets` with an absolute POSIX `root`, for example `/Users/alex/Documents`. This supplies synthetic file metadata and does not make the Mac an SMB server. APFS aliases/case policy remain pending. Experimental mounted SMB clients reuse `environment.storage.mappings`: select `client_access: auto` and `path_style: auto` or `mounted`, with an eligible mapping. Automatic Mac mount presentation is `/Volumes/<mapping-id>`; this is a synthetic allocation policy, not a claim about Finder naming. A mapping shared by Linux and Mac clients needs an explicit common `mount` or separate audience mappings. Native per-operation actors produce eCAR file evidence; the SMB transport has no invented user-process owner. Windows and Samba servers retain their own evidence. Native Mac SMB log messages remain unavailable.

Mac clients can use the shared `ssh_session` bundle against a modeled Linux receiver. The existing `source_ip` identifies the Mac; the event's `system` remains the receiver. An already active local GUI session can own the catalog-backed `/usr/bin/ssh` client, its Terminal/login/zsh ancestry and interactive history. Client evidence must fit before transport and remain alive through its close. Missing session/readiness or an unsupported executable leaves transport unattributed; it does not invent a login or convert SCP into SSH. Experimental Mac receivers use the same `ssh_session` event on an `architecture: arm64`, `type: workstation` target with `services: [ssh]`. Place the actor locally through existing `assigned_user` or `primary_system`; root/service-account login is unavailable. The bundle owns helper startup, audit credentials, shell readiness, transport and close. An existing paired `logoff` can set the receiver close time; the retained SSH continuation executes the close and survives checkpoint recovery. Type 10 `logon` is not the Mac authoring interface. SCP/SFTP receiver helpers and native Mac SSH messages remain unavailable.

Use existing `output.logs: [{format: macos_unified_log}]` to select the experimental macOS 26 arm64 workspace-entry export. An authored Mac `logon` with `logon_type: 2` creates a distinct local session; omitted `source_ip` stays local. Implicit baseline requests can reuse a live GUI session. A local interactive login owns a separate method-entry occurrence; the source records loginwindow as writer, not the session user. It does not establish desktop completion. Do not author internal `macos_workspace_request` events. Native Endpoint Security generation and other Unified Log event families remain unavailable. SSH-native close, SMB-native client logs, ES exit and final Gatekeeper rejection remain evidence gaps. Do not interpret prompting as denial, registration as activation, or a file write as execution. Intel/Rosetta, sleep/wake, roaming, Mac SMB serving, binary log archives and filesystem artifact production are excluded from this implementation.

The internal parser recognizes the bounded history profile and selected native exports. `eforge eval` discovers explicitly named `macos_unified_log.ndjson` and `macos_endpoint_security.ndjson` files, including per-host directories. Valid Unified Log completion objects are excluded from event counts. The ES reader admits historical v6 fork/exec/create/rename, v9 exec/exit and v10 fork only; unsupported pairs fail validation. Native roles, IDs, nanosecond text and privacy markers remain intact; normalized evaluation timestamps use microseconds. Directory provenance does not establish a native hostname or username. These readers validate structure and timestamps; complete native lifecycle and external ingestion checks remain open. Only the bounded Unified Log workspace-entry emitter is admitted. Selecting an output target does not establish SOF-ELK® or Splunk ingestion compatibility; no native Mac SIEM mapping is validated yet. Keep third-party records/derived exports ignored and author synthetic examples independently. Personal findings are not templates or fixtures.

Internal POSIX exec publication now has an eCAR `PROCESS/MODIFY` extension (`operation=exec`) preserving one PID/lifetime and previous/current execution IDs. This is not an upstream CAR action or a new authored event. Do not add `process_exec` to scenario YAML or infer native ES output from this capability; Native-source integration remains independently gated.

`process_audit_bind`, `process_privilege_drop` and `process_service_drop` are internal authenticated credential transitions, also rendered through the EvidenceForge eCAR `PROCESS/MODIFY` extension. They preserve execution identity and distinguish privileged audit adoption, authenticated-user credentials and pre-authentication `_sshd` service credentials. Service drops retain unknown audit origin. Do not author these event types or interpret them as native Endpoint Security callbacks. The bounded SSH bundle owns these transitions; they cannot be authored separately.

Internal `process_fork` renders eCAR `PROCESS/CREATE` with `operation=fork` and explicit parent/child execution IDs. It requires a State-owned fork; generic launches do not imply this operation. Do not author `process_fork` or infer native ES support from it.

Internal POSIX termination can retain an explicit exit code or termination signal/core indication. This is a terminal result, not proof inferred from a signal request, and it introduces no scenario field. Existing callers retain unknown outcomes. Bounded Darwin wait-status conversion does not enable native ES exit generation or validate a macOS 26 profile.

Internal process planning can retain an exact POSIX argument vector. It is not reconstructed from scenario or catalog command text. Fork inherits known arguments; exec replaces them, and missing new arguments remain unknown. Launchd activation requires the existing loaded definition's vector. No new authoring field or native ES exec profile is enabled.

Internal POSIX job control now owns explicit process-group and session lifetimes separately from login/audit IDs. Fork inherits known membership, exec preserves it, and groups/sessions can outlive their leaders. Authenticated membership transitions have an eCAR `PROCESS/MODIFY` extension (`operation=job_control`) with distinct actor/target roles and previous/current PGID/SID. This is not a scenario event or a new configuration field. Mac terminal login now creates an explicit POSIX session/group; its shell and child commands inherit it. Boot membership stays unknown. Internal launchd unload can atomically close an exact known group in child-first order; unknown membership retains its rejection guard; known outside-group children survive through exact same-transaction system-parent adoption. Loaded jobs retain their exact group after leader exit and binding expiry, including recovery. Full authored persistence orchestration remains pending. Do not infer membership from ancestry or advertise native ES metadata from this capability.

Internal POSIX process plans can also carry an explicit ordered launch environment. Fork inherits it; exec replaces it; missing values remain unknown and an empty vector means explicitly empty. Values are not expanded, converted to a mapping, or copied from the generator host. This metadata primitive adds no scenario field, mutable environment model, or native ES output capability.

Internal POSIX identities retain exact original/current parent lifetime references, separate from numeric PPIDs. Fork identifies its immediate parent and exec preserves these facts; old records remain unknown. Exact parent-exit adoption preserves the birth parent and historical observations while moving current ownership to an explicitly modeled live same-host PID-1 process. Group unload adopts surviving outside-group children without changing their group/session or credentials. Unknown parentage remains unsupported; native parent/responsible audit-token snapshots remain pending. No authored field is added.
