# 3.0.0rc1 release

## Snapshot and gates

`v3.0.0rc1` is an annotated tag on `dev` merge `87437876` (PRs #488, #491 and #500). Local gates
on that tree: routine suite and coverage 78.75% (20,601 passed); slow tier 2,228 passed after the
fixes recorded in the [ground-truth worklog](2026-11-17-ground-truth-acceptance.md).

## First release run (44423019779)

The run failed before any asset upload, so nothing was published:

- **Studio service and recovery (Windows):** `test_authoring_quit_choice_is_durable_and_stop_
  does_not_block_close` bounded session close with a 0.3 s wall clock against a 0.4 s fake
  interrupt; the runner took 0.375 s. The test now holds the interrupt until close has returned.
- **Slow shard 3/4 timed out at 60 minutes.** The shard planner balances by
  `.github/ci/timings.json`, whose slow profile had 80 cases and no 24-hour example generation.
  The five new draft generations landed by default cost; the planner's own projection with that
  seed gives 79 minutes for shard 3, matching the run (the other three projections equal their
  observed 47.7, 39.2 and 43.7). The profile now holds 1,674 measured durations (completed shard
  reports plus shard 3's log), the tier uses five shards (projected 42 minutes each), and the
  ceiling is 90 minutes.

Recovery follows `docs/releases.md`: the corrected workflow lands on `dev`, then
`gh workflow run release.yml --ref dev -f tag=v3.0.0rc1` repeats every gate on the tagged
commit. That snapshot still plans with its old seed (projected maximum 62.5 minutes on five
shards) and still contains the wall-clock Studio test. If that test fails again, the snapshot
cannot pass and the release moves to `3.0.0rc2`.

## Recovery run (44437411462)

Every build, the Windows Studio gate, portability, evaluation memory and slow shards 1, 2, 4 and
5 passed. Shard 3/5 failed once: `test_iteration_fresh_process_bytes_and_complete_evaluation
[default]` hit its 180 s `eforge eval` timeout. The test took 1,175.6 s against 548 s in the
recorded seed; locally, generation on the tag and on pre-branch `dev` is equal (221 s vs 223 s)
and eval is 98 s vs 89 s, so the runner was about 2.25x slow. Re-running failed jobs passed it.

The aggregate then failed: "CI evidence uses an unexpected shard count". Shards 1, 2 and 4 of
five had reused the first run's four-shard evidence at job start without executing. The reuse
fingerprint bound source, check ID and runner identity but not the shard count, which the
workflow (not the source) sets, so shard k of 4 matched shard k of 5 despite different cases.
The validator was correct. Sharded jobs now set `CI_SHARD_COUNT`, bound into the fingerprint,
and a workflow test keeps it equal to the run and validation counts. The tagged snapshot's own
`scripts/ci_evidence.py` predates that binding, so recovery dispatches now pass `force-tests`
to the slow tier: a recovery exists because the workflow changed.
