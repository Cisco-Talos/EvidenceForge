# EvidenceForge 2.0 manual scenario-authoring acceptance

## Scope

Run a manual clean-room Scenario 2.0 authoring exercise after PR #411 merged into `dev` at
`db8674e380539848676b50007e765b4fa420f10b`. This is the release-candidate/final-release manual
acceptance required while automated live-agent acceptance remains post-2.0 work.

The exercise used an isolated empty project root under `/private/tmp`, the merged checkout's
`eforge` executable, installed scenario-skill guidance, runtime `info` inventories, focused
`schema` selectors, and `eforge validate --json`. It did not inspect repository examples, select a
pack, create project configuration, or generate logs.

## Exercise

The authored scenario modeled an explicitly industry-neutral, fictional mid-sized software
company with:

- two users and four systems across Windows workstation, domain-controller, and Linux application
  roles;
- two internal network segments and one bidirectional Zeek SPAN sensor;
- typed local logon, bounded Git help, failed network logon, RDP, Windows process, SSH, and Linux
  process activity; and
- eight Windows, Linux/eCAR, and Zeek output formats.

The scenario was authored from runtime persona, role, and format inventories plus focused schema
selectors. A deliberately broad `eforge schema scenario --json` discovery call failed safely and
returned the exact supported selector list; subsequent queries used only supported focused
selectors.

## Results

The first complete authored draft validated with zero errors, two warnings, and one informational
storyline-pivot suggestion. One repair pass added explicit workstation-logon ownership and aligned
the SSH/application storyline actor. The final validation result was:

- status: `valid_with_warnings`;
- errors: 0;
- informational issues: 0;
- warnings: 1; and
- repair passes needed to reach zero errors: 0.

The retained warning states that the topology has no firewall sensor. It is intentional: this
exercise requests neither firewall policy/NAT modeling nor Cisco ASA output, so adding a fictional
firewall solely to silence the advisory would make the scenario less faithful to its stated scope.

No legacy public-identity overlay warning appeared in the clean project. Validation remained
non-writing and did not create `.eforge` state.

## Verdict

**PASS.** A new no-pack Scenario 2.0 exercise reached a structurally valid first complete draft,
the staged guidance led directly to the only useful semantic repairs, and the final remaining
warning was explicit, actionable, and intentionally out of scope.
