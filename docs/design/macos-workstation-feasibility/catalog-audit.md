# macOS application catalog audit

Every one of the 67 original application IDs has an availability decision below. “Supported” establishes native distribution availability, not completed EvidenceForge behavior or current-build native telemetry validation. Entries without a prefilled variant remain unavailable to generation. Shared IDs retain their existing Windows/Linux definitions; Windows-only tools are not renamed into Mac substitutes.

The initial managed Mac releases become available in the model on 2026-10-15, the catalog snapshot date, not a claim about their original release dates. Exact historical release windows can be supplied through existing deployment/catalog semantics. Homebrew paths model its standard Apple Silicon prefix; they do not inspect the generator machine. Host-bundled native services follow the scenario’s OS build. Public metadata and acquisition provenance remain ignored under `sample_data/macos/catalog-references/`. No personal inventories or usage distributions were used.

Additional Mac-native catalog entries cover launchd, loginwindow, native logind, syspolicyd, tccd, smd, mds, Safari, Finder, Terminal, login, zsh and Bash. This is an initial foundation; helper processes, update/network services and complete persona coverage remain implementation work. Native Mac logind must not acquire Linux systemd-logind messages.

Eighteen further native identities cover Dock, WindowServer, apsd, cfprefsd, configd, coreaudiod, corespotlightd, distnoted, installd, launchservicesd, mDNSResponder, mdworker_shared, nsurlsessiond, runningboardd, securityd, sharingd, trustd and usernoted. Their static paths come from the public Tahoe export, documented in `native-catalog-audit.yaml`. They are catalog-only: empty persona eligibility and a separate service category prevent automatic user-app or root boot activation. Service ownership, triggering and complete lifecycle remain separate implementation work. Ambiguous softwareupdated and Cryptex WebKit paths are not guessed into the catalog.

The machine-readable companion is `catalog-audit.yaml`; tests enforce exact original-ID coverage and agreement with admitted variants. No availability decision authorizes copying a publisher’s captured telemetry into fixtures.

Executable-path checks for the additional variants use the [Microsoft Edge installer](https://github.com/microsoft/shell-intune-samples/blob/master/macOS/Apps/Edge/installEdge.sh), [JetBrains launcher guidance](https://intellij-support.jetbrains.com/hc/en-us/articles/360011901879-How-to-start-IDE-from-the-command-line), [Sublime publisher forum](https://forum.sublimetext.com/t/4169-would-not-launch-on-mac/71151), and Homebrew formula installation contracts for [7-Zip](https://github.com/Homebrew/homebrew-core/blob/HEAD/Formula/s/sevenzip.rb), [.NET](https://github.com/Homebrew/homebrew-core/blob/HEAD/Formula/d/dotnet.rb) and [GCC](https://github.com/Homebrew/homebrew-core/blob/HEAD/Formula/g/gcc.rb). The .NET entry uses the native libexec executable rather than modeling the Homebrew wrapper as a binary; GCC retains its major-version suffix. SSH initially selects only its version query, pending the shared Mac SSH bundle.

The Office/Teams and Dropbox executable references are firsthand public diagnostic reports, used only for static path spelling. They are not compatibility or success guarantees. Microsoft installation scripts and Mozilla/Postman launcher documentation corroborate other paths. Application launches use independently authored argument-free commands; no captured identifiers, crash records, updater flags or workaround commands enter the catalog. Helper generation is limited to explicitly profiled, installed children with a supported parent and lifecycle contract.

The native launchd, loginwindow and logind entries explicitly identify their main executable format as `mach_o`. The previously acquired public [Mandiant Tahoe export](https://github.com/mandiant/macos-UnifiedLogs/releases/tag/v1.0.0) contains nonempty process image UUID metadata for these paths. Existing deployment/build/arm64 semantics determine the synthetic release image; no captured UUIDs are stored. Unknown image formats, including entries with only known signing metadata, remain unspecified, and helpers do not inherit the main executable's format assertion.

Chrome now catalogs renderer, GPU and generic utility/network helper executables under its existing `children` field. Their versioned paths follow Chromium’s [bundle construction](https://chromium.googlesource.com/chromium/src/+/HEAD/chrome/BUILD.gn) and [helper roles](https://chromium.googlesource.com/chromium/src/+/main/chrome/installer/mac/signing/parts.py), reviewed 2026-10-16. The commands contain minimal role arguments; sandbox/IPC tokens, Apéritif alternatives and native observations remain unmodeled. These are distinct installed binaries of the same managed release. Changing that release requires updating its versioned helper paths through the existing catalog overlay. No signing flags or Mach-O UUIDs are inferred from bundle membership. Helper intent now survives immutable compilation and uses exact installed-assignment materialization. The Mac GUI baseline selects a bounded subset through existing spawn-rule counts/delays, binds each child to the exact live browser and session, and uses ordinary process publication and session closure. Counts and delays are modeled, not empirically calibrated. Browser IPC, helper-attributed network flows and independent browser-quit orchestration remain outside this profile.
