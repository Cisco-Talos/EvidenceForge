## Recommendation

macOS workstation support is architecturally feasible, but it is a platform expansion, not an emitter-only feature. EvidenceForge already has suitable ownership boundaries for canonical events, action bundles, content identity, collection policy, and deterministic rendering. The principal work is making those boundaries express Mac behavior without inheriting Windows or Linux defaults. No product behavior was changed for this assessment.

Log sources are sufficient for the proposed macOS support. The scope is realistic Mac workstation behavior and the logs that observe it, consistent with EvidenceForge's existing focus. Here, **native Mac investigation means investigating Mac-native log sources**, not producing a filesystem artifact collection.

Pursue a shared platform foundation followed by two complementary log-source slices:

1. **Mixed-fleet hunting:** Mac-native activity rendered through the existing network sources, adapted eCAR, and a bounded, versioned Endpoint Security notification export.
2. **Native Mac log investigation:** selected Unified Log exports and Endpoint Security notifications, correlated with the same canonical activity. Shell history is an optional companion, consistent with existing bash-history support.

Give both use cases equal acceptance weight within that log-source scope. A network-only milestone offers useful network/server investigations; adding Mac endpoint sources enables local activity investigations. Shared process, account, file and network truth should make those sources agree wherever their collection capabilities overlap.

Generating LaunchAgent/LaunchDaemon plists, quarantine extended attributes, quarantine/TCC/browser databases or disk images is outside this proposal. Modeling a file change, launch item or policy decision may be necessary to generate correct logs; materializing the corresponding filesystem artifact is not. No delivery phase or acceptance gate below requires those artifacts.

Unified Log `.logarchive`/tracev3 containers and FSEvents are a separate distinction: they are native log storage formats, not a reason to require broader forensic artifact generation. Unified Log text/JSON exports are sufficient for the initial scope. Native container encoding and an optional FSEvents source would be independent log-format choices if a future consumer requires them.

The recommended first fixture target is **one pinned macOS 26 build on arm64**, with managed and unmanaged collection profiles. This is a proposed engineering boundary, not a claim of existing support or a statement about Apple's current support lifecycle. Intel, older releases, Rosetta, and multiple builds require additional fixtures and explicit compatibility claims.

### Shared truth that needs explicit Mac semantics

**Process and authentication identity.** A process lifetime and an executable image transition are different things. An exec can change the executable without allocating a new PID. A fork creates a different process. Audit identity, effective user, GUI session, remote authentication, parent process and responsible process must remain distinguishable. Apple's ES process data exposes audit tokens and signing metadata; the responsible process can differ from the parent. These facts belong in canonical identity/context/state, with source projections consuming them. The current `ProcessIdentity` freezes image, command and principal fields. Preserve published identity and historical observations: a design for linked immutable execution epochs under one process lifetime is preferable to rewriting a previously published identity when exec occurs. [Audit tokens](https://developer.apple.com/documentation/endpointsecurity/es_process_t/audit_token), [responsible process](https://developer.apple.com/documentation/endpointsecurity/es_process_t/responsible_audit_token), [signing metadata](https://developer.apple.com/documentation/endpointsecurity/es_process_t/team_id).

**Sessions and availability.** Local login, screen unlock, sleep, wake, logout, SSH and SMB authentication need distinct outcomes and ownership. Sleeping must suppress incompatible foreground activity without terminating every process or treating a collection gap as physical absence. If sleep is supported, timers, long connections and scheduled jobs require explicit resume behavior. Roaming also requires time-bounded addresses and sensor reachability; the current single `System.ip` boundary makes this a larger extension. The selected initial scope uses stationary, awake hosts; sleep/wake and roaming are deferred until the general entity-availability/network identity work is designed. Coordinate with that existing TODO item rather than introducing a Mac-only availability switch.

**Policy and outcome.** Gatekeeper assessment, TCC access decisions, SIP restrictions and XProtect detection/remediation must affect canonical success, denial and cleanup. A denied execution cannot produce a successful payload process or its downstream connections. Root access cannot be treated as automatic permission to modify SIP-protected locations. Managed configuration may change permitted actions, but management enrollment alone does not prove that a specific collection permission was granted. [Gatekeeper](https://support.apple.com/guide/security/gatekeeper-and-runtime-protection-sec5599b66df/web), [SIP](https://support.apple.com/guide/security/system-integrity-protection-secb7ea06b49/web), [privacy policy payloads](https://support.apple.com/guide/deployment/privacy-preferences-policy-control-payload-dep38df53c2a/web).

**Filesystem and executable identity.** Preserve observed path spelling separately from object identity. APFS defaults to case-insensitive behavior but supports case-sensitive volumes, so the current POSIX lexical path normalization is not a complete filesystem identity policy. Resolve modeled aliases such as `/var` and `/private/var` without consulting the generator machine's filesystem. Application bundles contain multiple files; a bundle ID, executable hash and code-directory hash are different identifiers. Model file versions, rename/copy/deletion and any quarantine or attribute state needed by the selected actions and log sources. These facts support consistent log records without producing files, extended attributes, databases or a filesystem image. APFS schema changes are needed when the selected workload uses modeled volumes or storage; a binary APFS writer is not needed. [Apple filesystem guidance](https://developer.apple.com/documentation/technologyoverviews/files-and-directories).

**Persistence.** A launch item can involve file creation, registration/loading, activation, execution, disabling and removal at different times. Use an action bundle and persistent state; do not equate writing a plist with successful execution. Emit only the observations supported by the selected log sources; the modeled plist need not be generated as a file. User agents and system daemons need different scope and activation conditions. Reuse service/task abstractions only where their semantics fit rather than translating launchd into Windows services or systemd units. [Apple launchd guide](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPSystemStartup/Chapters/CreatingLaunchdJobs.html).

### Native collection and tooling constraints

Apple provides Endpoint Security as an event API and `eslogger` as an inspection utility. Its notification export is practical for synthetic native-shaped records, but the output is not a stable API. Keep `schema_version` distinct from the ES message `version`. A pinned notification profile must not invent generic TCP FLOW or DNS-query events from Unix-domain socket notifications. Use network sensors or a separately modeled endpoint network collector for those observations. Actual collection permissions are fixture-capture prerequisites, not requirements for running the deterministic generator. [Apple Endpoint Security overview](https://developer.apple.com/videos/play/wwdc2022/110345/) and local `eslogger(1)`.

Unified Logging has source-specific retention and privacy semantics. Dynamic strings may be redacted, so perfect command lines, paths and usernames in every record would be unrealistic. Record the chosen privacy/level/filter profile in blind-safe collection metadata and preserve canonical truth separately. JSON export validates exported-record workflows; it cannot establish native archive compatibility. [Apple logging](https://developer.apple.com/documentation/os/logging), [privacy behavior](https://developer.apple.com/documentation/os/generating-log-messages-from-your-code), and local `log(1)`.

Validate initial log outputs against pinned export schemas, reference records and their intended ingestion parsers. Native archive readers are relevant only if native container output is later selected. For that optional extension, [Mandiant's macos-UnifiedLogs](https://github.com/mandiant/macos-UnifiedLogs) is a candidate independent parser; its documented string/format limitations mean it should not be the sole oracle. Artifact-tool compatibility is not an initial acceptance requirement.

Apple documents that FSEvents can coalesce changes and require rescanning. If this optional log source is selected later, preserve those semantics in its records and evaluate the chosen encoding separately. It does not make a filesystem artifact collection necessary. [Apple FSEvents guide](https://developer.apple.com/library/archive/documentation/Darwin/Conceptual/FSEvents_ProgGuide/UsingtheFSEventsFramework/UsingtheFSEventsFramework.html).

## Baseline and authoring requirements

A convincing workstation needs ordinary activity from the same lifecycle owners as storyline events. Add YAML profiles for Mac GUI/session processes, launchd-managed services, zsh/Terminal, browser helpers, office/developer applications, updater processes and permitted background network traffic. Installed software controls which processes and paths can appear. Retain persona timing, host/session-scoped RNG, jitter and realistic idle periods.

Model benign competition for the same persistence, shell and file surfaces used by the attack. Every Mac should not have identical launch items, a developer toolchain, Homebrew, elevated users, SSH enabled or an EDR deployment. Browser and application identity should drive network fingerprints consistently. Bonjour/mDNS, IPv6, QUIC, VPN and Private Relay behavior should be explicit future protocol/visibility choices where existing contracts do not support them; do not invent plaintext DNS or HTTP evidence to fill the gap.

### Public interfaces to revisit

No public schema is changed by this report. The implementation design should resolve these minimum interface needs before coding their dependent slices:

- Reuse `System.os`, `os_build`, `architecture`, services and roles. Require explicit architecture in new Mac examples and pin native export profiles to a build. Avoid silently changing legacy x64 defaults for existing scenarios.
- Add Mac identity overrides and effective collection/deployment profiles with explicit supported capabilities. Keep endpoint login identity separate from directory/SMB/SSO credentials.
- Expose semantic intent for login/unlock, execution, launch persistence, file attributes and policy outcomes. Reuse existing typed events where valid; add types only for distinct missing behavior. Do not require scenario authors to supply raw ES or Unified Log field dictionaries.
- Extend storage filesystem/presentation choices and Mac SMB client access modes as a coherent schema change. Existing Windows/Linux defaults and published pack closures remain intact.
- Select new source formats through the established output/catalog mechanism. Candidate names such as `macos_endpoint_security`, `macos_unified_log` and `zsh_history` are provisional, not documented supported values.
- Identify collection profile/build/export schema in manifests. Version event/context and checkpoint contracts where needed; do not promise restoration of incompatible pending Mac continuations. Preserve the existing behavior-aware resume policy.

## Delivery choices and dependency order

| Support option | Mixed-fleet hunting | Mac-native log investigation | Relative effort and principal risk |
| --- | --- | --- | --- |
| Network-visible Mac workstation | Useful network/server pivots | Limited; cannot reconstruct local activity | Medium-to-high shared foundation effort despite renderer reuse. Incorrect boot/process defaults can still contaminate the world. |
| Correlated endpoint plus exported native logs | Strong process/file/session/network chain | Useful investigations of native-shaped exported records | High; process/session identity, source coverage and versioned native fidelity are the main risks. Recommended first product boundary. |
| Optional additional log sources or native log encodings | Adds source-specific observations where useful | Enables additional log queries or native log-reader workflows | Source-dependent. FSEvents and native Unified Log containers require separate decisions; filesystem artifacts remain outside the proposal. |

### Proposed phases

1. **Fixture and contract gate.** Select an exact macOS 26 arm64 build and benign lab actions. Record enabled policies, collection permissions, ES subscription, export options and tool versions. Capture sanitized reference records on a test machine for local/SSH sessions, exec/fork/exit, file changes, downloads, policy denial and launch persistence. Pin candidate parsers and write an event-to-evidence coverage matrix. This gate supplies missing native semantics; manuals and an event-name list alone do not close it.
2. **Platform foundation and network milestone.** Unify classification; implement Mac identity, process/boot/session state, deployment profiles and source admission. Add representative Mac baseline activity and network/server correlation. Unsupported typed behaviors must produce actionable diagnostics. Establish ordinary login/logout and lock/unlock semantics; sleep/wake is deferred.
3. **Endpoint and Mac-native log milestone.** Add Mac eCAR plus a bounded ES notification subset and selected Unified Log NDJSON messages. Shell history can be added as an optional companion. Use common canonical owners, source-specific observation contracts and real fixture schemas. Include execution/file identity, supported authentication, one allowed and one denied policy outcome, and modest benign background activity. Both mixed-fleet hunting and Mac-native log investigation gates must pass; neither requires filesystem artifacts or native binary log containers.
4. **Remote access and persistence logs milestone.** Extend shared SSH in both directions and Mac SMB client behavior; add launch-item lifecycle and exact checkpoint continuation. Generate correlated process, file-change and launch-item observations where supported by the selected sources, without materializing plist files or attributes. Add additional security-control families only when reference evidence establishes their event semantics. A Mac RDP client is a later adapter; do not use `mstsc.exe` on Mac or claim a native Mac RDP server.

These four phases complete the proposed log-source scope. Additional sources such as FSEvents, or native `.logarchive`/tracev3 encoding, are optional extensions to assess only against a concrete log-consumer need. They are not required completion steps. Artifact production is not a follow-on phase in this proposal.

The high-effort dependencies are platform state/identity, SSH continuation semantics, Mac filesystem/SMB behavior, and reference-backed native source models. Adding a catalog string or format YAML does not complete any of those dependencies. Staffing/calendar estimates should be made after phase 1, using the chosen event subset and parser results.

## Acceptance scenarios and gates

| Scenario | Required evidence and negative controls |
| --- | --- |
| Ordinary mixed fleet | Mac workstation, Windows peer/server and Linux peer; stable accounts, native application trees, plausible background distributions and correct sensor observations. No Linux boot/systemd-logind semantics or Windows-local audit rows on Mac; native Mac logind remains valid. |
| GUI session | Login, lock/unlock and logout remain distinct. Source gaps do not change physical session state. Sleep/wake is deferred from initial acceptance. |
| Process execution | Fork creates a child; exec updates image identity coherently; exit closes the correct lifetime; PID reuse cannot join unrelated processes. Parent/responsible identity, audit identity and file hashes agree across sources. |
| SSH success/failure | Mac client to Linux and Mac receiver with Remote Login explicitly enabled. Transport precedes authentication; failed auth creates no successful shell; close and retry/resume emit once. No Linux logind identifiers on Mac. |
| SMB client access | Mac-to-Windows and Mac-to-Samba reads/writes; mount and credentials are native; server/network/client file bytes and identity agree. Unsupported server modes are rejected rather than approximated. |
| Download and execution | Network and endpoint log observations share destination file identity and execution outcome. Model quarantine/provenance where it affects the action or selected source; emit those fields only where observable. Encrypted content stays hidden from sources lacking visibility. No downloaded payload or quarantine attribute needs to be materialized. |
| Persistence | Logs of modeled plist write, registration, activation, process execution, unload and deletion form a valid timeline wherever the selected sources observe them. An inert or rejected launch item does not manufacture successful execution. No plist output file is required. |
| Blocked action | One fixture-backed Gatekeeper or TCC denial suppresses the denied effect; related visible records retain the attempted action. Protected-file attempts obey the configured SIP policy. |
| Collection limitations | No collector, disabled subscriptions, delayed/partial collection, privacy redaction and scenario boundaries yield only source-supported fields and events. Do not invent endpoint FLOW in eslogger. |
| Mac-native log investigation | Pinned log parsers recover expected fields, identities and timestamps from the selected exports; representative queries reconstruct the supported activity. Check source semantics beyond JSON syntax. Native archive readers and filesystem artifact parsers are not required. |

Cross-cutting acceptance:

- Same seed and resolved inputs produce identical evidence bytes across fresh processes and supported generator hosts. Scoped RNG changes must not perturb unrelated Windows/Linux output.
- Format filtering and parallel emission preserve canonical identities and the expected visible projection; collection changes must not alter whether the modeled action occurred.
- Stop/resume around fork/exec, session close, transfer, persistence and source buffering preserves exact output without duplicate or orphan terminal evidence. Retention stays bounded on long runs; version mismatches follow existing recovery rules.
- Native fixtures validate field types, optionality, timestamp precision, process-versus-target roles, redaction and version gates. Source defaults are measured, not guessed from one sample.
- External parser checks separately report syntactic ingestion, extracted fields and normalized semantics. Require measured SOF-ELK/Splunk mappings before claiming target support.
- Preserve current Windows/Linux behavior with focused contract tests and representative deterministic bundle comparisons. Add new routine tests for narrow contracts; put substantial mixed-fleet generation/fresh-process determinism in `slow` without coverage, and long-duration scalability diagnostics in `soak`. Retain normal release coverage/native gates when releasing.
- Use a domain-expert review of generated Mac evidence before claiming realism. This is a future acceptance gate, not a review performed during this assessment.

### Endpoint Security findings that affect implementation

1. **Process lifetime and execution identity must be separate.** All 614 SpriteTree exec events retain PID and process start time between the initiating process and target, while every target has a different `pidversion`. The executable changes in 598 cases; unchanged paths still produce a new execution identity. Apple SDK `ESMessage.h` explicitly describes these as before/after views of the same process with different program executions. Do not model every exec as a fresh PID or identify an execution by PID alone.
2. **Fork is a different transition.** All 382 fork events have a distinct child PID, matching child-parent PID relationship, and inherited executable path in this corpus. Fork and exec need separate canonical occurrences even when a higher-level action coordinates them.
3. **Identity roles cannot be collapsed.** Parent and responsible audit tokens differ in 2,347 records. Exec can change audit-session and credential fields; five exec pairs change effective UID. Keep audit identity, effective credentials, parent, and responsible process separate. These observations establish requirements, not population probabilities.
4. **Native serialization has meaningful nulls, arrays, and tagged unions.** Exec carries argument/environment arrays, working-directory file information, file descriptors, and an optional script file. Five script objects are present; the remainder are null. Team ID and TTY can be null. All observed process CDHashes are 40-character values, distinct from a content SHA-256. Preserve field meaning and optionality rather than filling every field with invented defaults.
5. **File destinations need source-native alternatives.** All 956 create notifications use the existing-file destination variant. Rename has 250 existing-file destinations and 280 new-path destinations, with the latter carrying a directory object plus filename. The SDK documents additional create-notification outcomes not present here; observed absence must not narrow the schema incorrectly. Canonical file identity, version, and path presentation should drive these renderings.
6. **Notification records can contain authorization-result information.** All SpriteTree rows have numeric notify action type and an authorization-result envelope. That envelope does not turn eslogger into an authorization-callback stream, and its allow value does not prove Gatekeeper accepted a later payload action.
7. **Source ordering needs explicit treatment.** Seven adjacent timestamp reversals occur across three files, and one file has per-event sequence resets. Do not assume capture order is always wall-clock order or infer one uninterrupted collector lifetime from a whole file. This corpus does not establish why those discontinuities occurred.
8. **Executable architecture is observable, but host architecture is a different fact.** The exec payloads include 505 ARM64 and 109 x86-64 image CPU types according to SDK constants. Keep architecture-aware profile selection; do not import the x86-64 examples into an arm64-only scenario or infer Rosetta/host architecture solely from these mixed files.

The ignored `analysis/endpoint-field-shapes.json` records field/type counts and `analysis/endpoint-summary.json` records the calculations. These are external research aids, not runtime configuration or checked-in fixtures. The existing public samples do not cover exit, open/write/unlink, SSH or GUI authentication notifications, launch-item notifications, policy-specific notifications, collection drops, or PID reuse after exit.

### Unified Log findings and behavior coverage

**The native NDJSON-format gap is substantially closed.** Apple successfully rendered the public archive with `--style ndjson --info --debug --signpost --timezone UTC`. The output includes ordinary log records, activity creation, signposts, user actions, state records, time synchronization records, and a final count/finished summary object. A parser must distinguish the completion object from an event. The log-record count exactly matches `log stats`; the stats also report nine loss events, so the exporter output must not be treated as a lossless one-to-one rendering of every internal record kind.

Fields include numeric process/thread/activity IDs and Mach timestamps, UUIDs, process and sender image paths, subsystem/category, native timestamp strings, format strings, and rendered messages. `messageType` occurs on log events, while signpost and activity records have different fields. Empty strings, omitted fields, null source values, and backtrace objects are observable. Preserve native casing and timestamp representation; do not substitute a third-party parser's normalized schema. The selected source can remain a bounded log-event subset, with other record kinds explicitly excluded unless implemented.

**Privacy affects evidence availability.** 598,651 exported event messages contain a private-data placeholder; other messages have masked/hash-like path representations. Keep canonical truth separate from the source's observable value. Do not derive a universal redaction probability from this archive or assume every path and user is recoverable.

### Privacy boundary for any later local inspection

No local inspection is part of this analysis. Keep personal records outside the checkout even though public data is ignored. Design and review a reducer before granting it log access: bounded time/source filters; allowlisted schema keys and types; counts; and predeclared behavior labels only. Do not return raw messages, arbitrary format strings, command lines, environment variables, application inventories, file paths, user/server names, addresses, UUIDs, or exact activity timestamps to tool output, chat, reports, or code. Free-form format strings can contain runtime data and are not automatically safe metadata. Redaction alone is insufficient.

For a new or unrecognized message, return an unknown-category count rather than a preview. If that cannot answer the question, prefer public evidence or a disposable test system. Author product examples and tests independently, using invented identities and documented public vocabulary; neither raw nor anonymized personal records become fixtures. The recommended next step is a small current-build schema/coverage probe, followed only by narrowly targeted behavior checks justified by its counts.
