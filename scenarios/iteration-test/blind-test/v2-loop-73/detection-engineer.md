# Detection Engineer — Authenticity Assessment
## Verdict
**Assessment:** Synthetic
**Verdict Confidence:** 76
**Synthetic-Confidence Score:** 64

## Executive Summary
The supplied corpus is likely synthetic, although it is substantially more production-like than a typical generated intrusion dataset. The six-hour window contains internally coherent Windows Security, Sysmon, eCAR, Zeek, ASA, proxy, web, and Linux evidence. Native Windows versions and fields are usually credible; process and session lifecycles are ordered correctly; Zeek protocol records consistently reference existing `conn.log` UIDs; and the principal intrusion sequence preserves realistic delays across endpoint, authentication, proxy, and network observations.

The synthetic assessment is not based on the compact storyline, broad cross-source agreement, absent event classes, shared timestamps, sanitized domains, or limited collection coverage. It rests primarily on two repeated source-native defects. First, 97 SMB-derived rows in `zeek-core/files.json` contain MD5, SHA1, and SHA256 values while declaring only the `MIME` analyzer, contrary to the file-analysis provenance represented elsewhere in the same Zeek data. Second, 24 Sysmon process-create records use a conspicuous all-or-nothing fallback: every version-resource field and the entire `Hashes` field are `-`, including well-known Microsoft and signed vendor executables, while 963 other process starts contain rich metadata and multiple hashes. A smaller Windows audit contract gap is visible in the newly created domain account's disabled-to-enabled transition: Event IDs 4720, 4724, 4738, and 4728 are present, but the expected 4722 enable event is not.

No decisive `hard_contradiction` was found. The conclusion is therefore “likely synthetic,” not “certainly synthetic.” The strongest counterweight is the corpus's excellent causal, lifecycle, and schema discipline across more than a million physical lines and tens of thousands of logical records.

## Evidence For Synthetic
- **[schema_or_format, contract_gap — high] Zeek digest fields contradict analyzer provenance.** `zeek-core/files.json` contains 651 records; 97 SMB file records declare `"analyzers":["MIME"]` while simultaneously populating `md5`, `sha1`, and `sha256`. Line 1 is a concrete example: `ts=1710763304.321895` (2024-03-18 12:01:44.321895 UTC), `fuid=FWBxMyApUC0ovOEFk`, `source=SMB`, filename `Procedures\\performance-summary-v2.xlsx`, all three digest fields populated, but no MD5/SHA1/SHA256 analyzer names. Lines 3 and 4 repeat the pattern for an Office presentation and a PDF. This is not merely missing source coverage: the row asserts completed hash outputs but omits the source-native analysis mechanisms that produced them. Other file-analysis records in the same directory do name `X509`, `MD5`, `SHA1`, or `SHA256` analyzers, demonstrating that the field is being used rather than globally suppressed. No corresponding mismatch appeared in `zeek-db/files.json` or `zeek-dmz/files.json`.

- **[environment_or_collection_plausibility, schema_or_format — high] Sysmon uses a selective catalog-like all-dash fallback.** Across 987 Sysmon Event ID 1 records, 963 have populated version metadata and hashes, but 24 records spanning 13 image names have all six fields set to `-`: `FileVersion`, `Description`, `Product`, `Company`, `OriginalFileName`, and `Hashes`. Examples include `C:\\Windows\\PSEXESVC.exe` on DC-01 at `2024-03-18 15:59:37.5653511Z`; built-in `C:\\Windows\\System32\\runas.exe` on WS-MCHEN-01 at `14:50:23.934Z`, `14:51:08.296Z`, and `14:51:24.790Z`; built-in `curl.exe` on WS-AJOHNSON-01 at `17:24:52.8406782Z` and `17:24:53.5502980Z`; and `msra.exe`. Signed/vendor executables also receive the same total fallback, including four Cisco AnyConnect `vpnagent` starts, four Microsoft Monitoring Agent `MonitoringHost` starts, three Veeam service starts, and one Thunderbird start. In contrast, ordinary `cmd.exe`, PowerShell, services, and other process starts on those hosts carry version resources plus MD5, SHA256, IMPHASH, and often SHA1 values. Per-image metadata absence can occur, but repeated simultaneous failure of version resources and all configured hashes for accessible, executing Microsoft/vendor binaries is difficult to reconcile with the otherwise functioning Sysmon configuration. The image-bounded fallback resembles incomplete synthetic application catalog entries.

- **[contract_gap — medium] The domain-account enable transition lacks Event ID 4722.** In `windows/DC-01-security.xml`, the account sequence is visible in the same audit channel: Event 4720 creates `svc_dirsync` at `2024-03-18 16:14:43.136Z`; Event 4724 sets its password at `16:14:44.777Z`; Event 4738 at `16:14:45.100Z` changes `OldUacValue=0x15` to `NewUacValue=0x10` and includes `%%2081` (account enabled); and Event 4728 adds it to Domain Admins at `16:14:48.012Z`. The file contains no Event 4722 anywhere among its 6,903 records. Because the same source captures the surrounding User Account Management events and explicitly records a disabled-to-enabled state change, this is a missing required companion event rather than a criticism of generally thin telemetry. Selective forwarding remains a possible real-data explanation, so this is not rated a hard contradiction.

- **[weak_signal — low] One credential-access sequence combines direct access and remote-thread semantics mechanically.** `windows/WS-AJOHNSON-01-sysmon.xml` starts `C:\\Windows\\System32\\ms-index-service.exe` at `2024-03-18 15:44:51.6544638Z` with command line `privilege::debug sekurlsa::logonpasswords`, records Event ID 10 access to `winlogon.exe` and then `lsass.exe` at approximately `15:44:57–15:44:58Z` with granted access `0x1FFFFF`, and records Event ID 8 at approximately `15:44:59Z` with `StartFunction=NtCreateThreadEx`. Sysmon's `StartFunction` represents the remote thread's entry routine, whereas `NtCreateThreadEx` is ordinarily the API used to create the thread. An unusual injector could create this observation, so it is only a weak semantic indicator, but it looks like two attack-technique templates joined without fully source-native remote-thread detail.

## Evidence For Real
- **Windows XML and Event ID semantics are broadly strong.** All inspected Windows XML parses successfully. Security events use plausible provider GUIDs, versions, tasks, opcodes, keywords, and native field names. Event 4624 is version 2, 4688 is version 2, 4689 is version 0, and Sysmon process/network/DNS events use plausible version 5 schemas. Across all Event ID 5156 records, the local-address role agrees with direction, with `%%14592` used for inbound and `%%14593` for outbound; no direction/local-IP contradiction was found.

- **Process lifecycles and identity correlations are unusually disciplined.** Across all Windows hosts, no Sysmon Event ID 5 termination precedes its Event ID 1 creation, no dependent Event ID 3/7/8/10/11/13 occurs before process creation or after termination, no child process is created before its visible parent, and no visible parent terminates before its child is spawned. DC-01 has 155 creates and 157 terminations with 148 paired GUIDs; DC-02 has 119/119 with 113 paired; FILE-SRV-01 has 111/109 with 106 paired. Security 4688/4689 records align closely with Sysmon 1/5, usually within roughly 0.04–0.64 seconds. eCAR IDs are unique, and no eCAR process termination or dependent actor use reverses its visible lifecycle.

- **Sysmon ProcessGuid construction matches native behavior.** The GUID for the DC-01 process created at `2024-03-18 16:14:39Z` contains the middle components `686f-65f8`; interpreted using Sysmon's timestamp encoding, `0x65f8686f` resolves to that exact UTC second. The PowerShell process at `17:42:27Z` similarly carries `7d03-65f8`, encoding its creation second. This is a subtle, source-native property that many superficial generators miss.

- **Security-log clearing has correct causal order and record-ID reset behavior.** On DC-01, Sysmon records encoded PowerShell at `17:42:27.684Z`, `cmd.exe /c wevtutil cl Security` at `17:42:30.253Z`, and `wevtutil.exe` at `17:42:30.379Z`. `windows/DC-01-security.xml` then records Event 1102 at `17:42:34.1403972Z` with subject `SYSTEM` and Logon ID `0x3e7`; its `EventRecordID` is 1. The next visible Security event is a 5156 at `17:42:36Z` with record ID 3. The clearing process terminates at `17:42:45Z`. The event ordering, identity, and channel reset are mutually consistent.

- **The remote-service and persistence chains contain required precursors.** On DC-01, Sysmon Event 11 creates `C:\\Windows\\PSEXESVC.exe` at `15:59:36.574Z`; Security Event 4697 installs `PSEXESVC` at `15:59:36.880Z` under subject `aisha.johnson`, Logon ID `0x5552f0f`; Sysmon Event 1 starts it under `services.exe` at `15:59:37.5653511Z`; and follow-on `whoami`/`hostname` commands start at `15:59:39.379Z`. A later sequence creates `DeviceSyncSvc` via `sc.exe` around `16:19:30Z`, records Event 4697 at `16:19:35Z`, and records scheduled-task Event 4698 at `16:19:36Z`. DC-02 similarly records `DirectoryCacheSvc` installation at `16:25:15Z`, execution beginning at `16:25:17Z`, and cleanup commands around `17:52Z`.

- **Exfiltration is consistent across endpoint, proxy, DNS, and network sensors.** WS-AJOHNSON-01 creates an archive after a `Compress-Archive` command beginning `17:01:09Z`, stages it at `17:16:15Z`, and starts `curl.exe` at `17:24:52.8406782Z`. Its Sysmon connection reaches proxy `10.10.1.35:8080` at approximately `17:24:57Z`. `proxy/access.json` lines 2340–2341 record a CONNECT to `api.westbridge-services.net` and a POST to `/upload/telemetry/7f3a2b19`, principal `MERIDIANHCS\\aisha.johnson`, client port `56096`, and `18,783,114` client bytes. `zeek-dmz/conn.json` line 7647 records the same client-to-proxy source port at `1710782697.801`; proxy DNS follows at `1710782697.932`; and proxy-origin TLS starts at `1710782698.005`, carrying approximately 18.8 MB. The transport precedes DNS/application evidence by plausible subsecond offsets and preserves tuple and byte-scale relationships without impossible equality.

- **Zeek UID, tuple, and protocol ordering are coherent outside the files-analyzer defect.** The core sensor has 11,712 connections, 2,969 DNS records, 1,723 HTTP records, 389 SSL records, 651 file records, 230 SMB-file records, and 132 SMB-mapping records. The DB sensor has 438 connections; the DMZ sensor has 8,345. Across DNS, HTTP, SSL, SMTP, and SMB records, every inspected UID resolves to a `conn.json` row, tuple fields agree, and no protocol record predates its connection. File `conn_uids` also resolve without appearing before their connections. SSL certificate FUIds resolve to file/X.509 observations with plausible order.

- **Firewall lifecycle texture is credible.** `network/asa.log` contains 19,553 messages: 6,460 TCP builds (302013), 6,459 TCP teardowns (302014), 971 UDP builds and 971 UDP teardowns, 1,876 translation creates and 1,876 translation deletes, 320 denies, and paired byte counters. Exactly one TCP connection remains open at the end of the bounded window; there are no orphan teardowns or teardown-before-build cases. Teardown reasons vary (`TCP FINs` 4,221, `SYN Timeout` 2,092, `Reset-O` 103, `Reset-I` 43), and PRI/severity values agree with message severity.

- **Authentication and workload distributions are not trivially uniform.** The two DCs contain 788 TGT requests and 2,131 TGS requests spread across AES256, AES128, and RC4; 818 successful logons span types 2, 3, 5, 7, 9, and 10; and the 33 failures distinguish bad-password and disabled-account substatuses. DHCP records show multiple lease lengths and renewal jitter rather than exact fixed intervals. Linux shell history includes ordinary command diversity and at least one visible typo (`ddf`), while proxy, web, and ASA records include varied status, duration, byte, and closure outcomes.

## Detailed Analysis
The corpus covers approximately `2024-03-18 12:00Z` through `17:59Z`. The physical files total 1,353,463 lines, with high-volume single-line JSON and multi-line Windows XML. All JSON-lines inputs parsed without malformed records, and the Windows XML documents parsed successfully. This does not by itself establish authenticity, but it allowed field-level rather than presentation-level evaluation.

Windows Security volumes fit host roles. DC-01 has 6,903 events, led by 4,456 firewall permits, 1,098 TGS requests, 406 TGT requests, 275 logons, and 155 process creations. DC-02 has 6,126 events with a similar but non-identical mix: 3,892 permits, 1,033 TGS, 382 TGT, 262 logons, and 119 process creations. FILE-SRV-01's 1,325 records include 5140/5145 share access and 4656/4658/4663 object-access chains that are absent or uncommon on workstations. This is appropriate role differentiation, not a single copied distribution.

Security Logon IDs and subjects remain stable through the important chains. The PSEXESVC installation uses `0x5552f0f` for the named subject rather than borrowing SYSTEM's `0x3e7`, while the log-clear event correctly uses SYSTEM. Service logons, network logons, remote interactive logons, special-privilege assignments, and matching logoffs show plausible identities and ordering. Some sessions and processes begin before or end after the bounded observation window; these were not counted as defects.

Endpoint/network relationships are also credible. Sysmon Event ID 3 and Security 5156 volumes are highest on the domain controllers, proxy, and service systems; workstation processes initiate browser, update, administration, and proxy traffic under plausible principals. eCAR contains 25,560 FLOW CONNECT records, 2,049 PROCESS CREATE records, 1,893 PROCESS TERMINATE records, 756 PROCESS OPEN records, 2,284 MODULE LOAD records, and 10 THREAD REMOTE_CREATE records. Persistent pre-window processes explain actor IDs without in-window creates; among visible lifecycles there are no causal reversals.

The strongest realism is temporal. The corpus avoids exact identity between independently observed sources: Windows Security generally trails Sysmon process evidence by small, varying fractions of a second; proxy CONNECT and POST observations follow the client process and transport; proxy-origin DNS and TLS are close but not simultaneous; service installation occurs after file placement and before service execution. Zeek connections have durations and close states, ASA has corresponding lifecycle outcomes, and Windows process/session records include termination evidence. Similar filesystem timestamps were not considered.

The strongest authenticity weaknesses are localized rendering and contract defects. The Zeek digest/analyzer inconsistency repeats 97 times in one source family, making accidental corruption of a single row unlikely. The Sysmon all-dash pattern similarly clusters by image identity rather than looking like sporadic host load, permissions, or collector loss. Those patterns are characteristic of deterministic rendering paths in which known catalog entries receive complete metadata while fallback entries receive no metadata. The missing 4722 also appears inside an otherwise fully represented account-management chain. Together, these defects outweigh the extensive realistic detail, but only moderately because a real sanitized export could conceivably have enrichment rewriting and selective collection rules.

No conclusion was drawn from the sanitized-looking domain names, the ease of following the intrusion, the lack of unrelated Sysmon event types, the relatively narrow time window, or the unusually complete cross-source joins. Those attributes are explicitly non-diagnostic without a concrete source-native consequence. Likewise, broad consistency was counted as evidence for realism, not inverted into an allegation of synthesis.

## Realism Score by Category
- **Field format accuracy:** 7/10 — Windows, eCAR, firewall, proxy, and most Zeek schemas are strong, but the repeated Zeek analyzer/digest mismatch and categorical Sysmon metadata fallback are significant source-native defects.
- **Temporal patterns:** 9/10 — Process, authentication, service, proxy, DNS, TLS, connection, and cleanup sequences have credible causal order and varied observation offsets; no lifecycle reversal was found.
- **Cross-source correlation:** 9/10 — Logon IDs, PIDs/GUIDs, UIDs, tuples, ports, principals, byte scales, and service/file relationships align well without relying only on exact timestamp matching.
- **Behavioral realism:** 8/10 — Baseline roles and intrusion behavior are plausible and include cleanup and lifecycle evidence; the remote-thread representation and account-audit omission reduce confidence.
- **Environmental consistency:** 7/10 — Host-role volumes, authentication mix, shares, proxying, and firewall behavior are credible, but the image-specific Sysmon fallback is difficult to explain as an organic collector condition.

## Recommendations
1. Make Zeek file-analysis provenance authoritative. Whenever `md5`, `sha1`, or `sha256` is populated, include the corresponding analyzer in `analyzers`; otherwise omit the digest. Add a validator over every `files.json` row so this contract cannot diverge by source such as SMB versus X.509.

2. Replace the Sysmon all-dash application fallback with source-native behavior. Known Windows and signed vendor binaries should receive realistic version-resource fields and hashes consistent with the host build and binary identity. If a hash or metadata lookup is intentionally modeled as failed, make failures sparse and field-specific instead of setting every field to `-` for every occurrence of an image.

3. Complete the Windows account-management event contract. When Event 4738 visibly changes an account from disabled to enabled and User Account Management auditing is active, emit the matching Event 4722 with the same target SID, account, domain, subject, and causally compatible timestamp.

4. Review Sysmon Event 8 semantics. Use a credible remote entry routine/module for `StartFunction` and reserve `NtCreateThreadEx` for the creation method implied by the behavior. If the intended action is credential dumping through direct process memory access only, Event 10 may be sufficient and Event 8 should be omitted.

5. Preserve the existing strengths: native EventRecordID reset after log clearing, Sysmon-style ProcessGuid timestamp encoding, process/session lifecycle completeness, UID/tuple integrity, source-specific timing offsets, and role-dependent event volumes. Future realism work should target these concrete contract defects rather than making the storyline less complete or adding unrelated event types.
