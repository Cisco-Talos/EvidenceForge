## Verdict

**Assessment:** Real

## Executive Summary

The logs look more like sanitized production telemetry than a synthetic corpus: the six-hour environment is noisy, role-aware, and internally coherent, and the principal intrusion can be followed through plausible transport, authentication, execution, staging, transfer, persistence, and cleanup pivots without a visible causal impossibility. A few collection and texture artifacts remain—notably a missing source-side PsExec process, an unattributed staging-file read, selective SSH lifecycle gaps, and repeated shell-command templates—but they are moderate clues rather than decisive generator fingerprints.

The apparent source, `10.10.1.35`, has an outbound SMB FLOW in `WS-AJOHNSON-01.meridianhcs.local/ecar.json` line 797, but neither that host's eCAR nor its Security/Sysmon XML contains a `psexec` process or command. This is not impossible—process collection could miss it and SMB can be attributed to PID 4—but it removes a normally valuable source pivot despite otherwise active Event 1/4688 collection.
- [contract_gap] The staged database file loses actor ownership at a critical relay step. `DB-PROD-01.meridianhcs.local/ecar.json` lines 601-603 attribute the 17:30:25 `scp /tmp/rpt_0318.sql.gz root@10.10.2.30:/tmp/.cache/rpt_0318.sql.gz`, outbound flow, and file read to root/PID 886591. `APP-INT-01.meridianhcs.local/ecar.json` lines 751-754 then show the inbound SSH flow, root sshd child, login, and file creation, but line 756 records the subsequent `/tmp/.cache/rpt_0318.sql.gz` FILE/READ with no actorID, PID, principal, or source-process fields even though line 755 shows the outbound SMB relay. The asymmetric loss of source ownership is a concrete hunting-contract weakness.
- [environment_or_collection_plausibility] `APP-INT-01.meridianhcs.local/syslog.log` line 240 contains only `pam_unix(sshd:session): session closed for user root` for PID 1937270 at 17:30:51. The same PID's connection/authentication/open sequence is absent from syslog even though eCAR lines 751-754 place the complete in-window SCP session at 17:30:29-36. Later SSH sessions on the same host are fully represented in syslog—connection, accepted public key, PAM open, logind creation, PAM close, and logind removal at lines 245-261—so this is a selective source-local lifecycle gap rather than merely thin source coverage. Similar close-only SSH PIDs occur elsewhere, although some can legitimately be pre-window sessions.
- [distribution_texture] Exact long administrative command templates recur across unrelated host/user histories more often than ideal. Across 263 visible bash-history commands, 44 distinct command strings repeat; examples include the exact `systemctl show sshd -p ActiveState -p SubState -p MainPID` in `DB-PROD-01.../aisha.johnson.bash_history` line 8 and `PROXY-01.../marcus.chen.bash_history` line 8, and the exact `journalctl -u NetworkManager --since '2 hours ago' --no-pager | tail -30` in `DB-PROD-01.../marcus.chen.bash_history` line 44 and `LOG-MON-01.../aisha.johnson.bash_history` line 16. - [weak_signal] Several attack-side operations materialize with exceptionally clean semantic labeling in eCAR—for example `SERVICE/CREATE`, `THREAD/REMOTE_CREATE`, and explicit `FILE/READ`/`WRITE` transitions. Completeness itself is not evidence, and I did not score it as such; the weak concern is limited to the few places where that otherwise rich attribution abruptly disappears, especially APP-INT line 756.

## Evidence For Real

- The dataset has credible scale and source mix for the visible environment. It spans approximately 12:00-18:00 UTC across Windows workstations, domain controllers, file/mail servers, Linux application/database/mail/monitoring systems, proxy, web, firewall, IDS, and three Zeek vantage points. I counted 32,914 eCAR records, 24,289 Windows Security/Sysmon events, 19,241 Zeek connection records, 18,175 ASA lines, 2,262 proxy requests, and 706 web requests—enough background that the intrusion is genuinely embedded rather than isolated.
- Baseline behavior is role-specific and operationally messy. Linux logs include CRON/sysstat, unattended upgrades, rsyslog queueing, sudo/PAM, irqbalance, multipath, snapd, logind, failed SSH, and package/application administration. Windows evidence includes DNS/Kerberos/LDAP chatter, file-share access, monitoring and backup explicit-credential use, browser/Office/Teams activity, scheduled tasks, service processes, workstation lock/unlock, RDP, failed logons, and noisy legitimate process access to LSASS by services, Defender, and core Windows processes.
- Zeek traffic has believable state and service diversity rather than a single success-heavy path. `zeek-core/conn.json` contains 10,960 connections with 8,719 `SF`, 1,914 `S0`, 146 `RSTO`, 89 `RSTR`, 30 `REJ`, plus `OTH`, `S1`, `S2`, and `S3`; major services include DNS, Kerberos, HTTP, LDAP, SMB, TLS, syslog, SSH, DHCP, SMTP, and RDP. `zeek-dmz` adds heavy unsolicited/incomplete traffic (2,645 `S0` of 7,847 connections), while `zeek-db` is appropriately dominated by MySQL.
- DNS texture is broad. `zeek-core/dns.json` has 2,913 records across 865 queries, with A, AAAA, PTR, SRV, TXT, NS, MX, and SOA types and a mix of 2,675 NOERROR, 216 NXDOMAIN, 16 SERVFAIL, and 6 REFUSED responses. Repeated queries have irregular intervals, and infrastructure names, reverse lookups, WPAD failures, OCSP, update, development, and user-service destinations coexist.
- Network causal ordering holds. For matched Zeek application records, all 2,913 core DNS, 1,484 core HTTP, 329 core SSL, 46 SMTP, 363 SMB-file, and 216 SMB-mapping records occur after their associated connection start; the same is true for the inspected DB and DMZ protocol records. Endpoint FLOW observations may lead or lag the network sensor by sub-second/low-second collection latency, but no examined source initiation appears after the dependent authentication in a way that makes the activity impossible.
- Endpoint process ownership is unusually strong in a good way. Of 5,390 eCAR events whose actor/source UUID resolved to one of 1,929 visible process creations, none occurred before the referenced process was created. No process object with both lifecycle endpoints terminated before its visible creation. This supports a coherent underlying state model but is not, by itself, treated as a synthetic clue.
- Firewall lifecycle evidence is consistent. `fw-perimeter/cisco_asa.log` contains 6,961 TCP/UDP build records and 6,961 matching teardowns, with no teardown before its build and no teardown lacking a visible build. It also contains NAT build/teardown pairs, ACL denies, and ICMP lifecycle records. The mix of zero-duration UDP, longer TCP, denied traffic, and inbound scan noise is operationally plausible.
- The principal kill chain works technically. At 16:00, SMB from `10.10.1.35` reaches DC-01 before PSEXESVC installation and SYSTEM command execution. At 16:14, WmiPrvSE-spawned commands create `svc_dirsync`, set its password, and add it to Domain Admins; Windows Security EventRecordIDs 28256993-28257012 record 4720, 4724, 4738, and 4728 with one consistent SID ending `-8222`. At 16:20, `DeviceSyncSvc` and an hourly task are created; at 16:25, `DirectoryCacheSvc` is installed and run on DC-02. These are coherent persistence/lateral-execution artifacts rather than disconnected keywords.
- The collection/staging/exfiltration chain is especially convincing. APP-INT initiates SSH to DB-PROD at 17:14:49; DB syslog lines 177-180 show connection, root password acceptance, PAM open, and logind session 279031. `mysqldump` at 17:17:23 creates `/tmp/rpt_0318.sql`, which is later compressed and sent via SCP at 17:30:25. Zeek observes `10.10.4.10:46790 -> 10.10.2.30:22` with an `SF` 20.406-second SSH session and realistic bidirectional byte counts, followed by APP-INT's SMB relay to FILE-LNX and a receiver-side authenticated `svc_mhsync` file write.

DC-01 eCAR lines 5339 and 5347 show `wevtutil cl Security`; the Security log then records Event 1102 at 17:41:59 and EventRecordID resets to 1 before climbing to 813 by the window end. ## Detailed Analysis

### Scope, collection, and hunt orientation

The visible window is a six-hour Monday slice, roughly 2024-03-18 12:00:00 through 18:00:00 UTC. Host naming and observed addresses suggest user systems in `10.10.1.0/24`, core services in `10.10.2.0/24`, DMZ systems in `10.10.3.0/24`, and the production database at `10.10.4.10`. The apparent key mappings are stable in the logs: DC-01=`10.10.2.10`, DC-02=`10.10.2.11`, FILE-SRV-01=`10.10.2.20`, FILE-LNX-01=`10.10.2.21`, MAIL-EDGE-01=`10.10.2.25`, MAIL-CLIN-01=`10.10.2.26`, MAIL-FIN-01=`10.10.2.27`, APP-INT-01=`10.10.2.30`, LOG-MON-01=`10.10.2.40`, WEB-EXT-01=`10.10.3.10`, and PROXY-01=`10.10.3.20`.

This placement is supported by both ordinary and suspicious traffic. DCs receive dense DNS/Kerberos/LDAP and SMB/SYSVOL activity; FILE-SRV and FILE-LNX show user/document access; DB-PROD is MySQL-heavy; WEB-EXT receives large volumes of incomplete internet-origin traffic; PROXY receives internal CONNECT/HTTP requests and originates external sessions. Source volume is not uniformly spread: DC Security logs are much larger than workstation logs, DMZ Zeek has far more `S0` traffic than the database sensor, and Linux syslog density differs substantially by role.

### Signal-to-noise and baseline texture

The suspicious activity does not dominate the corpus. On DC-01, for example, the Security stream contains 6,732 events, led by 4,203 WFP 5156 records, 1,070 Kerberos 4769 events, 414 4768 events, and hundreds of logon/lifecycle records; the rare attack-relevant account/service/task/log-clear events are singletons or pairs. Workstations show hundreds of WFP events mixed with process creation/termination, interactive sessions, registry changes, DNS, browsing, and occasional failures. The IDS streams likewise contain background policy alerts, public scanning, P2P/STUN, suspicious-TLD lookups, and false-positive-prone JA3 signatures rather than only storyline-specific detections.

The baseline is not perfectly organic. Exact shell-command reuse across hosts is the clearest distribution concern, and some source families appear curated. Nevertheless, the timing itself is not uniformly spaced: user and infrastructure events occur in bursts, DNS intervals vary substantially, server noise continues throughout the window, and external scans generate incomplete and reset connection states.

### Kill-chain reconstruction and pivot feasibility

The first high-confidence lateral-execution pivot is PsExec to DC-01. `WS-AJOHNSON-01` emits an SMB flow from `10.10.1.35:61990` at 16:00:21.101. DC-01 records a successful type-3 `aisha.johnson` session at 16:00:21.808, an inbound SMB flow at 16:00:22.072, `C:\Windows\PSEXESVC.exe` creation at 16:00:22.902, service creation at 16:00:23.169, service process creation at 16:00:25.200, and child command execution at 16:00:31.428. The source PsExec process is missing, but the target sequence itself is technically sound.

Privilege and persistence follow. At 16:14:31, SYSTEM-owned WmiPrvSE spawns `cmd.exe /c net user svc_dirsync MhsSvc!2024 /add /domain`, then `net.exe`; at 16:14:36, the same WMI parent path launches the Domain Admins group addition. DC-01 Security records the expected user lifecycle with a consistent account SID. At 16:20:17-31, the same WMI lineage creates `DeviceSyncSvc`, registers a SYSTEM hourly task, and writes the SCHTASKS prefetch file. DC-02 then receives an authenticated `marcus.chen` type-3 session and service-control traffic before `DirectoryCacheSvc` creation at 16:25:08 and SYSTEM execution at 16:25:11. The user/SYSTEM transitions match remote service-control semantics.

The data-access chain begins with APP-INT root SSH to DB-PROD. The network connection starts before DB sshd records connection, password acceptance, PAM open, and logind session creation. All subsequent database commands share session 279031 and a stable shell/process lineage. `mysqldump` creates the SQL file, `gzip` creates the archive, and `scp` both reads the archive and opens the exact SSH tuple seen in Zeek. APP-INT receives it under root, then opens `10.10.2.30:50395 -> 10.10.2.21:445`; FILE-LNX accepts `svc_mhsync` via NTLMSSP and writes the same basename under `ClinicalResearch/Integration/DB-Staging`. This provides practical pivots by username, session, process UUID, tuple, filename, and destination.

The final cleanup is likewise linked. DC-01's WMI lineage clears Security, and the EventRecordID reset corroborates the effect. The temporary domain account is deleted later; DC-02's persistence service is stopped and deleted from WmiPrvSE-spawned commands under the established `marcus.chen` logon; APP-INT root clears history and writes `/root/.bash_history`. These steps are operationally plausible and do not depend on unsupported narrative assumptions.

### Lifecycle and contradiction checks

I found no visible dependent-before-initiator contradiction. Process actor UUIDs resolve backward to already-created processes; process terminations do not precede visible creates; Zeek DNS/HTTP/TLS/SMTP/SMB application records follow connection starts; the principal SSH, SMB, RDP, Kerberos, and service-control sequences have plausible ordering. The visible RDP sessions use successful `SF` transport with multi-minute durations and substantial bidirectional bytes, while scanner-origin RDP attempts are `S0` with zero application bytes.

The main lifecycle defect is selective omission, not reversed causality. APP-INT's root SCP session has a close-only syslog record despite a fully visible eCAR session and despite complete same-host syslog sequences for later SSH logins. The unattributed eCAR file read at the relay boundary similarly breaks an otherwise useful ownership chain. These would slow or weaken a real hunt but do not make the underlying activity impossible.

### Tradecraft realism

The tradecraft is credible for hands-on-keyboard enterprise intrusion: PsExec/SMB remote execution, WMI-hosted commands, temporary privileged account creation, service and scheduled-task persistence, RDP/SSH administration, database-native collection, gzip staging, SCP transfer, SMB relay into a shared integration location, Security log clearing, service/account deletion, and shell-history clearing. Command syntax is operationally usable, process parents are appropriate (`services.exe`, WmiPrvSE, shell), and privilege transitions are coherent.

The activity is detectable and somewhat noisy, but that is not inherently synthetic. PsExec leaves PSEXESVC and service-install telemetry; account creation produces standard audit events; database staging uses obvious filenames; and cleanup itself is logged. Real intrusions, red-team exercises, and insider operations often leave exactly this kind of uneven footprint.

## Recommendations

If this were synthetic, the highest-value improvements would be:

- Preserve source-process visibility for remote-administration bundles when the source host otherwise has process telemetry. For the 16:00 PsExec chain, emit or retain the actual PsExec client process and link it to the outbound SMB/service-control activity, or deliberately model a source-local process-collection drop consistently.
- Keep actor/process ownership through multi-hop file transfers. `APP-INT-01` line 756 should identify the process or service that reads the SCP-staged archive for SMB forwarding, matching the process/session quality already present on the DB and FILE-LNX legs.
- Make SSH collection gaps source-coherent. If PID 1937270's connection/auth/open messages are dropped, model an explicit local collection gap affecting the lifecycle group rather than leaving only the close while adjacent sessions on the same host are complete.
- Increase per-person shell vocabulary and sequencing. Retain common commands, but reduce exact reuse of long parameterized strings across unrelated users/hosts and introduce more operator-specific aliases, flags, path choices, typos, corrections, and task-local follow-up commands.
- Preserve the current strengths: role-weighted source volumes, mixed Zeek states, noisy internet scanning, credible authentication/process lifecycles, and concrete cleanup consequences. These are the main reasons the dataset reads as production-like.
