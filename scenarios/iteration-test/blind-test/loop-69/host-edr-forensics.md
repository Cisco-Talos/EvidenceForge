# Host/EDR Forensics Analyst — Authenticity Assessment
## Verdict
**Assessment:** Inconclusive (slight synthetic lean)
**Verdict Confidence:** 58/100
**Synthetic-Confidence Score:** 53/100

## Executive Summary
The endpoint records show several convincing source-native behaviors and cross-source joins: Windows process IDs and images align across Security, Sysmon, and eCAR; macOS fork/exec and SSH evidence retains process identity; and Linux SSH/PAM sessions have coherent opens and closes. I found no decisive hard contradiction, but the highly synchronized six-hour collection window, limited macOS Unified Log sample, and templated-looking repetition in some shell histories leave a mild synthetic signal.

## Evidence For Synthetic
- **[distribution_texture] Linux shell histories:** histories for shared operator accounts recur across several unlike server roles and repeatedly use short, broad diagnostic command sets. Examples include Marcus Chen's systemd-resolved/Samba checks on `FILE-LNX-01` and `APP-INT-01`, and Aisha Johnson's journalctl, disk, and service checks on multiple Linux hosts. This is possible in real operations, but the repeated generic checks across distinct systems look more like a reusable activity pattern than host-specific troubleshooting. It is a weak-to-moderate clue, not a contradiction.
- **[environment_or_collection_plausibility] Window synchronization:** nearly all eCAR and host event families cover Monday 2026-11-02 from roughly 13:00 through 19:00 UTC. For example, `DC-01` Security runs 13:00:04–18:59:50 UTC and its eCAR runs 13:00:04–18:59:50; both macOS endpoint streams similarly span about six hours. A shared export window is plausible, but the alignment across many sources is unusually uniform and mildly synthetic-looking.
- **[environment_or_collection_plausibility] Sparse Unified Log:** each Mac has only two or three Unified Log entries in the visible six-hour window despite Terminal use, multiple SSH sessions, and other activity in zsh history and Endpoint Security/eCAR. Unified Log collection may be filtered, so this is a coverage question rather than proof of missing required events.
- **[weak_signal] Linux service checks:** histories sometimes query names that differ from the active service naming visible in the host family (for example, `systemctl status smb-client` and `cifs-utils` on `APP-INT-01`). Such operator shorthand and stale service names occur in production; their repetition alongside other generic commands modestly increases the texture concern.

## Evidence For Real
- **[schema_or_format] Native Windows event structure:** Security XML retains Event IDs and named EventData fields; Sysmon includes familiar ProcessGuid, ParentProcessGuid, Image, and command-line fields. On `WS-MCHEN-01`, Security 4688 at 2026-11-02 13:09:13.453Z records `mstsc.exe /v:MAIL-FIN-01`, NewProcessId `0x1c50` (decimal 7248), while Sysmon Event 1 at 13:09:13.210Z records PID 7248, the same image, command line, and explorer parent. eCAR creates the same PID and image at 13:09:13.359Z. These are coherent, source-native joins.
- **[contract_gap absent; positive lifecycle evidence] Windows lifetimes:** on `WS-MCHEN-01`, the scheduled `taskhostw.exe` created at 13:11:31.380Z has a matching Sysmon termination at 13:11:36.597Z. On `WS-AJOHNSON-01`, Microsoft Defender's `MpCmdRun.exe -SignatureUpdate` appears as a Security 4688 and Sysmon Event 1 near 13:06:44Z, followed by Sysmon Event 5 at 13:06:49Z. The process records have plausible service ancestry and durations.
- **[cross-source correlation] Windows RDP and eCAR:** `WS-MCHEN-01` records `mstsc.exe /v:MAIL-FIN-01` at 13:09:13Z and an outbound eCAR TCP flow to 10.10.2.27:3389 at 13:09:16.179Z. The flow is a few seconds after process start, consistent with a client starting transport. The inspected record does not itself prove the target-side logon, but it presents no ordering inversion.
- **[cross-source correlation] Linux SSH lifecycle:** `PROXY-01` records a connection from 10.10.1.31:49700 at 16:19:19Z, successful public-key authentication and PAM session opening at 16:19:25Z, then session close at 17:00:47Z. A pre-auth connection from 10.10.4.10 is closed without a login at 16:28:47Z, a realistic failed/abandoned path. Linux syslog uses RFC5424-style PRI/version/timestamp fields and normal sshd, sudo, PAM, CRON, and daemon messages.
- **[cross-source correlation] macOS process/session evidence:** on `MAC-MROSS-01`, loginwindow's workspace message at 13:03:18.726Z is near the eCAR local session login at 13:03:19.582Z. Endpoint Security shows launchd → xpcproxy → Terminal exec progression at 13:07:45Z, and the zsh history begins with `id`, `sw_vers`, and `uname` at 13:07:48–13:07:57. At 16:01:48Z the eCAR SSH flow from 10.10.1.42:51790 to 10.10.1.41:22 precedes the sshd-session accepted-key Unified Log message at 16:01:52.965Z. PID, audit-token, and exec-version transitions should be read as fork/exec state changes, not as a sequence of unrelated processes.
- **[distribution_texture] Varied role volumes:** DCs have abundant Kerberos and Windows Filtering Platform events; file servers show SMB access/auditing; the proxy and web host have much larger network volumes than workstation eCAR streams. That shape is plausible for the host roles inferable from names and records, rather than every machine having the same event mix.

## Detailed Analysis
- **Process trees and sessions:** The sampled Windows trees are plausible: explorer launches the user's `mstsc.exe`, while `services.exe` launches service processes and `svchost.exe` parents `taskhostw.exe`. The `WS-MCHEN-01` mstsc example is a strong three-way PID/image/command-line match across Security, Sysmon, and eCAR. eCAR's RDP flow follows launch. Windows logon IDs and process IDs are not interchangeable: Security 4688's `ProcessId` is the creator PID, while `NewProcessId` is the child PID; treating the former as the launched process would create a false mismatch. Logon type 3 sessions on `FILE-SRV-01` often close within seconds, consistent with network file access. On domain controllers, high 4768/4769 and 4624/4634 volumes are consistent with domain authentication load. Visible session endings are not uniformly present, but bounded-window starts and ends can account for unmatched rows.
- **Windows Security/Sysmon:** Common event formats and field names are credible. Process creation and termination counts are close on the sampled workstations and Windows servers, with legitimate exceptions for long-lived, pre-window, or unobserved processes. Sysmon Event 3/22 and Security 5156 form large network families; their volume alone is not a synthetic indicator. The inspected events contain no demonstrable PID or parent-image contradiction. Some eCAR process creations have no exact Sysmon Event 1 counterpart, but source coverage differences and filtering can explain that without a visible causal violation.
- **Linux syslog and history:** Linux hosts expose diverse service and workstation activity: `sshd`, `sudo`/PAM, `systemd-logind`, CRON, package services, rsyslog, networking, and desktop services. Successful SSH entries show connection → authentication → PAM session open, with closures for several sessions inside the window; pre-auth disconnects are also present. Histories use epoch comments and commands that suit the apparent host roles, including database inspection on `DB-PROD-01`, Samba checks on `FILE-LNX-01`, and development work on `WS-LNGUYEN-01`. The histories are operationally broad and sometimes generic; they lack command exit statuses and cannot alone prove that each command completed. I did not treat absent pre-window SSH initiators or post-window session endings as defects.
- **macOS ES, Unified Log, and eCAR:** The Endpoint Security files identify schema version 1 and ES version 11, and include audit tokens, PID versions, process start times, parent tokens, and executable metadata. eCAR expresses process lifecycles in normalized CREATE/MODIFY/TERMINATE records; its fork and exec changes preserve execution IDs, PID, and changing audit identity. This is compatible with macOS process semantics and should not be judged as if each exec were a separate fork. Unified Log is much thinner than the Endpoint Security/eCAR coverage, but its few entries align with session startup and sshd authentication. The two Macs show reciprocal SSH activity at different times and local user history is consistent with those connections. The sparse Unified Log remains a weak collection-profile concern, not a proven missing companion.
- **eCAR correlation:** eCAR entries are generally time-ordered and carry coherent host, actor, PID, image, session, and network tuple fields. For example, the macOS inbound flow precedes server authentication; on the Windows workstation the launched RDP client precedes its port-3389 flow. The report does not infer unsupported relationships from a flow with no process identity or require every normalized row to have a separate native event in the files shown.

## Realism Score by Category
- **Field format accuracy: 8/10** — Windows XML, RFC5424-style Linux syslog, macOS ES tokens/Unified Log JSON, and normalized eCAR fields are convincing.
- **Temporal patterns: 7/10** — Local ordering and process/session timing look plausible; the broad shared six-hour boundary is conspicuously synchronized.
- **Cross-source correlation: 8/10** — Sampled process IDs, images, command lines, sessions, and SSH/RDP tuples align across sources.
- **Behavioral realism: 7/10** — Host-role behavior and noisy ordinary activity look plausible; several Linux histories repeat generic checks across hosts.
- **Environmental consistency: 7/10** — The mixed Windows, Linux, and macOS fleet and role-specific volume are credible; the Unified Log sample is unusually sparse relative to endpoint activity.

## Recommendations
- If this were synthetic, vary the routine Linux diagnostic command sequences more by host role and operator, and avoid repeating the same clusters of generic checks across unrelated servers.
- If this were synthetic, model the macOS Unified Log collection scope explicitly or include a more representative selection of relevant log entries; keep filtering as a collection property rather than adding arbitrary entries to force matches.
- If this were synthetic, vary the visible source collection boundaries or document the common export window through the log timestamps themselves only when the source supports it. The present synchronized window is a weak texture signal, not a standalone defect.
