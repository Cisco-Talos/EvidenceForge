# Threat Hunter — Authenticity Assessment
## Verdict
**Assessment:** Synthetic
**Verdict Confidence:** 78
**Synthetic-Confidence Score:** 72
## Executive Summary
The corpus is most likely synthetic, but it is a high-quality construction. It covers approximately six hours on 2024-03-18 (12:00–18:00 UTC) and contains 126,239 logical records or non-empty log lines across 21 endpoint hosts, three Zeek sensors, two Snort sensors, a perimeter firewall, a proxy, web access logs, Linux syslog, shell history, Windows Security events, Sysmon, and eCAR-style endpoint telemetry.

The endpoint and network evidence is operationally convincing. Process parents precede children; dependent process activity occurs within process lifetimes; short-lived services terminate; Windows account and service operations have source-native audit companions; SSH transport precedes authentication and shell activity; SCP and SMB file movement preserve direction, identity, and timing; and an explicit Security-log clear produces a believable EventRecordID reset while Sysmon and endpoint evidence remain intact. These observations were credited for their concrete semantics, not merely because the sources match neatly.

The synthetic verdict is driven by three independent, repeated defects. First, 831 UFW SYN records draw TCP receive windows almost uniformly from exactly three values, including repeated scanner identities whose TTL and packet length stay fixed while the window profile changes. Second, successful responses for four fixed, unauthenticated web routes behave like independent draws from a broad bounded byte range rather than content-backed page sizes. Third, all 83 ECDSA certificates in the DMZ Zeek X.509 stream encode an empty RSA exponent and omit the EC curve. None is a single-record anomaly. Together they form a generator or normalization fingerprint strong enough to outweigh the otherwise excellent realism.

I did not use filesystem timestamps, external DNS resolution, missing Sysmon event types, thin coverage by itself, narrative completeness, or mere cross-source agreement as authenticity evidence. I found no defensible `hard_contradiction` and no clear `contract_gap` after checking the relevant companion sources.

## Evidence For Synthetic
- **[distribution_texture] TCP fingerprints vary like independent categorical draws.** In `WEB-EXT-01.meridianhcs.local/syslog.log`, all 831 UFW blocks are TCP SYN records, and `WINDOW` has only three values with near-equal corpus frequencies: 1024 in 288 records, 14600 in 272, and 65535 in 271. This is not just global endpoint diversity. For source `185.220.233.25`, all 175 packets have TTL 117 and length 52, yet its windows split 63/51/61 among 65535/14600/1024. Lines 1, 22, and 24 show that same source and fixed packet profile using each window value at 12:00:18, 12:02:51, and 12:05:00. Source `185.220.88.13` is similarly stable at TTL 45 and length 60 across 208 packets but splits 60/75/73 across the same three windows; lines 7, 60, and 77 exhibit the switches. Multiple machines behind a scanner address are possible, but the same three choices and near-uniform mixing recur across the entire firewall stream. That looks like per-record random selection from a short pool rather than stable TCP-stack behavior.

- **[distribution_texture] Fixed web routes have unconstrained, nearly uniform response sizes.** In `WEB-EXT-01.meridianhcs.local/web_access.log`, the 58 HTTP 200 responses for `/about`, `/products`, `/blog`, and `/login` have 58 distinct byte counts spanning 5,603–79,403 bytes. Each route is independently all-unique: `/about` 13/13 (5,603–79,403), `/products` 18/18 (6,736–71,435), `/blog` 15/15 (5,679–77,075), and `/login` 12/12 (23,594–71,755). The combined values populate every 7.5-KB band from roughly 5 KB through 80 KB. Concrete examples include `/about` at line 93 with 44,605 bytes, line 380 with 17,512, and line 426 with 57,372; none has a query string or authenticated-user field. Dynamic rendering, localization, compression, and device variants can change sizes, but they normally produce route-specific clusters or recurring templates. One broad, non-repeating draw per request across four stable public routes is a strong synthetic distribution.

- **[schema_or_format] EC certificate metadata is systematically encoded in an RSA-shaped field set.** `zeek-dmz/x509.json` contains 83 records with `certificate.key_type:"ecdsa"`, `certificate.key_alg:"id-ecPublicKey"`, and a 256-bit key. Every one has `certificate.exponent:""`, and none has `certificate.curve`. Line 12 at 2024-03-18 12:07:49.816993 UTC (`CN=api.opsgenie.org`), line 13 for its issuer, and line 32 for `CN=www.cloudflare.com` all exhibit the same shape. In source-native X.509 semantics, an RSA exponent is inapplicable to an EC public key, while the named curve is the meaningful key parameter. An exporter could introduce this normalization defect, so this is not a hard impossibility; its 83/83 consistency nevertheless exposes a schema-generation or flattening fingerprint.

## Evidence For Real
- **Process lifecycles are internally sound at scale.** Across 33,946 eCAR records, no checked dependent event precedes its referenced process creation, no dependent event follows that process's termination, no process terminates before creation, and no duplicate process identity was found. Equivalent ProcessGuid checks in 11,690 Sysmon records found no create/dependent/terminate inversion. Processes already alive before the six-hour boundary and still alive at its end were treated as boundary-censored, not as defects.

- **The Windows remote-service sequence has realistic source-native ordering.** On `DC-01.meridianhcs.local/ecar.json`, `C:\Windows\PSEXESVC.exe` is created by System at line 3519 (16:00:27.732), the `PSEXESVC` service is created at line 3520 (16:00:27.998), the service process starts under `services.exe` at line 3522 (16:00:28.587), and its child executes `cmd.exe /c whoami && hostname` at line 3530 (16:00:30.118). Windows Security records include Event 4697 for the service and process-audit records, while Sysmon includes the file creation and process chain around lines 107335–107562. The sequence reflects distinct file, service-control, and process phases rather than collapsing them into one event.

- **Account and persistence activity has the expected administrative audit trail.** On DC-01, eCAR lines 3737–3758 capture `net user svc_dirsync ... /add /domain` and addition to Domain Admins. The Security stream then records Events 4720, 4724, 4738, and 4728 between 16:15:28 and 16:15:33. The later `DeviceSyncSvc` service and hourly scheduled task commands appear in eCAR lines 3845–3860, Security Events 4697 and 4698, and Sysmon process telemetry. On DC-02, `DirectoryCacheSvc` is created at 16:25:25, runs as SYSTEM under `services.exe` at 16:25:28, terminates, and is explicitly stopped and deleted near 17:52. The identities and timing differ by source in plausible ways while preserving the underlying action.

- **Linux staging and transfer form a coherent multi-protocol lifecycle.** `DB-PROD-01.meridianhcs.local/ecar.json` records `mysqldump` creating `/tmp/rpt_0318.sql` at line 536, `gzip` creating `/tmp/rpt_0318.sql.gz` at line 541, and `scp` starting at line 543. Line 544 opens TCP `10.10.4.10:47871 -> 10.10.2.30:22`, and line 545 reads the staged gzip file. The receiving SSH process on APP-INT-01 creates `/tmp/.cache/rpt_0318.sql.gz` at eCAR line 800. That file is then observed moving from APP-INT-01 to FILE-LNX-01: `FILE-LNX-01.../syslog.log` lines 455–457 show SMB open/write/close by `svc_mhsync`, its eCAR line 1192 records the write, and `zeek-core/files.json` line 577 reports a complete 1,424,627-byte SMB gzip object with zero missing bytes. This is useful pivot evidence because the transport, authentication, process, and file semantics agree without impossible ordering.

- **Anti-forensics respects collection boundaries.** APP-INT-01 executes `history -c && cat /dev/null > ~/.bash_history` at eCAR lines 847–848, and WEB-EXT-01 executes `shred -u /root/.bash_history`; their empty root-history artifacts are therefore explainable rather than missing coverage. On DC-01, `wevtutil` clears Security at about 17:42. Security Event 1102 becomes EventRecordID 1, and later Security records continue from the reset sequence while independent endpoint/Sysmon telemetry still retains the initiating process evidence. That is the expected asymmetry of clearing one Windows channel.

- **Network accounting and sensor views are plausible.** The three Zeek `conn.json` streams contain 20,261 connections with a varied state mix (`SF`, `S0`, `REJ`, `RSTO`, `RSTR`, `OTH`, `S1`, `S2`, and `S3` where appropriate). No negative duration was found, no successful `SF` flow had an empty packet side, and no IP-byte count fell below the minimum implied by packet counts. DMZ external addresses are diverse rather than drawn from a tiny conspicuous pool. Zeek TLS certificate references resolve to X.509 records, validity intervals cover the observation time, and inspected issuer/subject chains and SNI/SAN relationships have no concrete contradiction.

- **Routine traffic has role-specific texture.** DCs are dominated by Kerberos, WFP connection, and machine-account activity; the proxy is flow-heavy; Linux hosts have distinct combinations of SSH, systemd, package, mail, database, Samba, and kernel activity. The 48 DHCP records show stable MAC/IP/hostname relationships and renewals near half-life with jitter for 3,600-, 7,200-, and 14,400-second leases. This does not prove authenticity, but it argues against a shallow attack-only fabrication.

## Detailed Analysis
- **Scope and integrity.** Only records under `review-data` were used as evidence. The set contains 68,300 JSON records, 30,219 XML event records, 27,020 non-empty `.log` lines, and 700 shell-history lines. All inspected NDJSON decoded successfully, and the Windows XML documents parsed without malformed records. Similar filesystem timestamps were ignored.

- **Collection profile.** The data describes 21 endpoint hosts spanning Windows workstations, domain controllers, Windows and Linux file servers, application/database systems, mail systems, proxy, monitoring, and a DMZ web server. Endpoint eCAR exists on every host; Windows systems contribute Security and Sysmon; Linux systems contribute syslog and selected shell history. Network visibility is divided among core, database, and DMZ Zeek sensors, with perimeter/core IDS and ASA firewall telemetry. The mix is broad but not implausibly identical across hosts.

- **Authentication and session behavior.** The corpus contains successful and failed Windows logons, Kerberos TGT/TGS activity, explicit-credential use, SSH/PAM/logind sessions, and SMB authentication. Checked short-lived sessions have closure evidence when the close falls within the slice. At the slice edges, existing processes and sessions were not penalized. Failed Windows authentication around 14:59 from `LT-MRIVERA-02` to workstation/DC targets and later privileged actions provide feasible identity and host pivots, but the verdict does not rely on that storyline being easy to reconstruct.

- **Host/network temporal relationships.** Endpoint flow directions resolve consistently against each host's local address. For the checked SSH/SCP, RDP/remote-administration, proxy upload, SMB, and service-control sequences, transport opens before the corresponding authentication or application action and closes after it. Small source-to-source timestamp offsets are present rather than exact timestamp cloning. Zeek UID, tuple, file, and TLS relationships are internally coherent. No concrete cross-source tuple, principal, PID, LogonID, filename, byte-count, or direction contradiction was found in the investigated chains.

- **Tradecraft realism.** The activity includes native administrative tools, service creation, WMI ancestry, scheduled tasks, encoded PowerShell, archive staging, explicit proxy use, Linux database export/compression/SCP, SMB staging, account creation/removal, and channel/history clearing. Parent-child and privilege transitions are mostly credible, including service execution as SYSTEM below `services.exe` and root SSH child activity on Linux. The presence of these steps was not counted as proof of reality; their lifecycle quality was.

- **Signal-to-noise and investigative value.** The attack-relevant records sit among substantial Kerberos, service, browser, TLS, package-management, mail, SMB, scan, STUN, BitTorrent, and ordinary system noise. Common pivots—hostname, account, PID/ProcessGuid, LogonID/session ID, network tuple/UID, Zeek file UID, path, hash, service/task name, and certificate fingerprint—are available. Coverage is sufficient for hunting without requiring every source to observe every action.

- **Defect severity.** No record proves physical impossibility, so the result does not merit an 81–100 synthetic-confidence score. The UFW and web-size distributions are nevertheless repeated hundreds or dozens of times and are independent of the X.509 field defect. Their breadth makes chance or one-off sanitation less persuasive than synthetic construction. The score therefore falls in the “likely synthetic” band rather than “confidently synthetic.”

## Realism Score by Category
- **Field format accuracy:** 7 — Windows, eCAR, syslog, firewall, proxy, web, IDS, and most Zeek fields are structurally credible, but the systematic EC-certificate exponent/curve shape is a material source-native defect.
- **Temporal patterns:** 9 — Process, service, session, transport, transfer, DHCP renewal, and log-clear sequences have plausible ordering and non-identical source delays; no checked lifecycle inversion was found.
- **Cross-source correlation:** 9 — Identity, process, tuple, UID, file, service, and task pivots work across the major source families without a concrete contradiction. The score reflects semantic consistency, not completeness alone.
- **Behavioral realism:** 8 — Administrative and attacker behaviors use credible tools, ancestry, privileges, and lifecycle phases amid ordinary activity. The web response-size distribution prevents a higher score.
- **Environmental consistency:** 7 — Host roles, protocols, sensor placement, background services, DHCP, and routing are coherent, but the UFW scanner fingerprint mixing is difficult to reconcile with stable source packet profiles.

## Recommendations
1. Preserve TCP-stack identity across repeated packets from a modeled origin. Derive window, MSS/options, TTL, packet length, and IP-ID behavior from one stable source profile; vary them only when a concrete host/NAT population change explains the variation.
2. Make web response bytes content-backed. Give each route a stable base representation, then model bounded changes from templates, authenticated state, compression, localization, pagination, or explicit dynamic payloads. Repeated public routes should form explainable clusters rather than independent draws from a global range.
3. Emit X.509 key parameters according to key algorithm. RSA records may carry `certificate.exponent`; EC records should omit that field and populate the appropriate curve value in the source-native Zeek shape.
4. Add distribution-level regression checks, not only record validation: per-source TCP fingerprint cardinality, route-conditioned response-size reuse/variance, and algorithm-conditioned certificate fields would have detected all three scored indicators.
5. Retain the existing lifecycle and correlation quality. The strongest parts of the corpus are the ordered service/process chains, SSH/SCP/SMB transfer semantics, bounded-window handling, and realistic separation between Security-log clearing and independent endpoint visibility.
