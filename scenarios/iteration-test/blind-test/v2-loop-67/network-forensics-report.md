# Network Forensics Analyst — Authenticity Assessment
## Verdict
**Assessment:** Synthetic
**Verdict Confidence:** 74
**Synthetic-Confidence Score:** 65
## Executive Summary
The network evidence is unusually strong for synthetic telemetry: it has credible protocol diversity, independent sensor UIDs and clock offsets, coherent firewall/NAT lifecycles, realistic packet loss, valid TCP-state/history combinations, DNS cache behavior, TLS resumption, proxy tunnel accounting, and a convincing multi-stage lateral scan and SSH session. I found no decisive impossible route, port, TLS cipher, certificate-validity, TCP-state, NAT-allocation, or visible lifecycle ordering.

The synthetic verdict instead rests on three concrete, repeated artifacts. First, 18 Zeek core DNS connections model an apparent retransmission by adding a packet/history symbol without adding the corresponding DNS payload bytes. Second, both Snort sources place every port-bearing alert in nearly identical, tightly bounded approximately 0.25-second delay bands relative to the associated Zeek connection, including first-packet DNS rules whose alert timestamp should normally track the triggering packet rather than a sampled processing delay. Third, the public-facing certificate population is substantially more one-host/one-certificate and one- or two-SAN than a mixed production Internet population. A weaker fourth signal is that every Zeek JSON file, including `conn.json` files containing sessions lasting hours, is strictly sorted by the logged start timestamp.

These artifacts raise the result into the “likely synthetic” band, but the absence of a hard contradiction and the depth of realistic cross-source behavior keep confidence moderate rather than decisive. Filesystem timestamps and real-world DNS resolution were not used.
## Evidence For Synthetic
- **`contract_gap` — DNS retransmission counters do not carry retransmitted payload bytes.** In `zeek-core/conn.json`, 18 of 2,977 UDP DNS UIDs represented in `dns.json` have two packets on one side but only one DNS transaction and only one message's payload bytes. At `2024-03-18T12:00:31.150223Z`, UID `CQCGxQKougSoDWDAQw` (`conn.json` line 3; `dns.json` line 1) records `history="Ddd"`, `resp_pkts=2`, `resp_bytes=57`, and `resp_ip_bytes=113`. The IP-byte arithmetic is exactly 57 payload bytes plus two 28-byte IPv4/UDP headers, leaving the second response datagram with zero payload. At `12:03:12.197778Z`, UID `CQ5Q1a7Z9TmsSJ9vRDA` (`conn.json` line 32; `dns.json` line 17) records the converse: `history="DDd"`, `orig_pkts=2`, `orig_bytes=56`, and `orig_ip_bytes=112`. All 18 cases are queries for `DC-01.meridianhcs.local` or `DC-02.meridianhcs.local`; 12 are extra-originator and six extra-responder cases. An isolated empty UDP datagram is technically possible, but this repeated, narrowly targeted pattern is much more consistent with a retry model incrementing packet count/history without duplicating payload accounting.

- **`distribution_texture` — Snort timestamps occupy matching synthetic-looking delay envelopes at two sensors.** All 62 TCP/UDP alerts in `snort-core/snort_alert.log` match a Zeek core 5-tuple and fall `0.214115–0.314003` seconds after the corresponding `conn.ts` (median `0.260535`, mean `0.258453`, standard deviation `0.022350`). All 83 TCP/UDP alerts in `snort-perimeter/snort_alert.log` that can be compared the same way match Zeek DMZ and fall `0.216792–0.312683` seconds after `conn.ts` (median `0.254641`, mean `0.257493`, standard deviation `0.025920`). Restricting the comparison to DNS-query alerts still gives `0.214115–0.314003` seconds for 52 core alerts and `0.217793–0.312683` seconds for 32 perimeter alerts. For example, the `.top` query alert at `03/18-12:04:32.489802` in `snort-core/snort_alert.log` corresponds to the Zeek DNS transaction for `metrics-ehpksvft.top` but is offset by `0.214115` seconds. The nearly duplicated bounded delay distributions across two source pairs look like per-source latency sampling, not packet-capture timestamps from the triggering DNS datagrams.

- **`distribution_texture` — Certificate identity ecology is over-specialized.** In `zeek-dmz/ssl.json` and `zeek-dmz/x509.json`, 473 TLS observations expose a leaf chain. In 469 of 473, the leaf CN exactly equals the SNI and the SNI appears literally in the SAN list. The 182 unique leaf fingerprints each map to exactly one observed SNI; 469 leaf observations have only one or two DNS SANs, and only 66 observations (35 unique leaf certificates) contain any wildcard. This is valid record-by-record, but a six-hour mix containing Microsoft, Google, Amazon, CDN, package, SaaS, and organization services would ordinarily expose more shared, wildcard, and multi-SAN certificate identities. OCSP scheduling has a similar generated texture: for issuer-name/key hash `f52569...`/`e04044...`, six serials use seven different response windows ranging from `14.881` to `137.181` hours in `zeek-dmz/ocsp.json`; another issuer group ranges from `16.883` to `166.347` hours.

- **`schema_or_format` — all Zeek files are globally ordered by event start time.** Every JSON log in `zeek-core`, `zeek-dmz`, and `zeek-db` has zero timestamp inversions. That includes all three `conn.json` files even though they contain long sessions: the `10.10.3.10:54236 -> 10.10.2.30:22` SSH flow starts at `14:14:36.481736Z`, lasts `13,342.181861` seconds, and appears at line 4,994 of 11,354 in `zeek-core/conn.json`, positioned by start rather than the `17:56:58.663597Z` close. Native Zeek connection records are commonly emitted on connection finalization, so this is evidence of generated or post-processed ordering. A SIEM export could deliberately sort on `ts`, so this remains a weak source-format signal rather than a contradiction.
## Evidence For Real
- The six-hour observation window is populated at credible scale: `zeek-core/conn.json` has 11,354 records, `zeek-dmz/conn.json` 8,432, and `zeek-db/conn.json` 475. Core traffic includes 6,046 TCP, 4,884 UDP, and 424 ICMP connections with nine connection states; DMZ includes 7,063 TCP, 1,056 UDP, 313 ICMP, and nine states. TCP `SF`, `S0`, `RSTO`, `RSTR`, `REJ`, `S1`, `S2`, `S3`, and `OTH` histories agree with packet direction and reset/close behavior in the tested records. No IP-byte/header lower-bound violation was found, and no active 5-tuple overlap was found despite legitimate tuple reuse.

- Independent observation points behave independently. There are no UIDs reused across `zeek-core`, `zeek-dmz`, and `zeek-db`. Of the DMZ connections, 4,292 can be paired to a core observation by tuple and time; their UIDs differ, while the core clock is generally about `0.114` seconds later. The paired records include small timestamp, duration, packet, and loss differences rather than being copied rows. DNS observations preserve answers and TTLs while RTT and timestamps vary slightly by vantage point.

- Firewall state is exceptionally coherent. `fw-perimeter/cisco_asa.log` contains 7,476 parsed TCP/UDP build records with unique, contiguous connection IDs `1681558–1689033`, 7,473 matching teardowns, and exactly three connections left open in the bounded window (`1688122`, `1688143`, and `1688782`). It also contains 1,882 dynamic NAT builds and 1,882 teardowns with no orphan, local-tuple mismatch, or overlapping PAT-port allocation. Of the 7,476 builds, 7,428 match a Zeek DMZ 5-tuple near the firewall timestamp. Teardown reasons agree at scale: 4,171 matched DMZ `SF` flows end with `TCP FINs`, 2,092 `S0` flows end with `SYN Timeout`, 78 `RSTO` flows with `TCP Reset-O`, and 51 `RSTR` flows with `TCP Reset-I`.

- Firewall enforcement is visible on the correct side of the traffic. The 321 `%ASA-4-106023` denies include DMZ-to-inside and inside-to-DMZ attempts. The matched Zeek observations are all one-sided `S0` records with zero response packets: 287 appear at the DMZ observation point and 30 at core. For example, the deny at `12:12:46` for `10.10.3.10:45280 -> 10.10.2.20:445` maps to a DMZ `S0` record with `history="S"`, one origin packet, and no response.

- Proxy accounting has realistic tunnel and capture-loss behavior. `PROXY-01.meridianhcs.local/proxy_access.log` has 2,678 records: 1,560 `CONNECT`, 1,089 `GET`, and 29 `POST`, with 200, 206, 301, 302, 304, 403, 404, 407, 502, 503, and 504 outcomes. All 715 `tunnel_id` groups have one setup row, consistent client identity/source port, and one to ten inspected HTTP rows whose byte sums equal the setup row's `tunnel_cs_bytes`/`tunnel_sc_bytes`. At `12:02:07`, the `www.office.com` tunnel reports 1,989 total client bytes and 44,870 total server bytes. The DMZ Zeek flow records exactly 1,989/44,870; core records 1,989/44,540 with `missed_bytes=330`. This is a persuasive capture-vantage loss pattern, not merely exact cross-source matching.

- HTTP behavior has static and dynamic texture. `WEB-EXT-01.meridianhcs.local/web_access.log` contains 763 requests from 105 source addresses, including 695 GET, 42 HEAD, 14 OPTIONS, and 12 POST requests. Outcomes include 357 status 200, 215 status 404, 78 status 403, 51 status 304, and smaller 2xx/3xx/4xx/5xx populations. Static objects retain exact sizes—for example, 20 successful requests for `/assets/css/main.min.cdfb17fb.css` are 37,108 bytes—while dynamic pages such as `/products`, `/blog`, `/about`, and `/login` vary. Of 194 plaintext web requests paired to Zeek DMZ HTTP records, all have matching status and user agent and 190 have exact response-body byte counts; the four apparent byte differences are in ambiguous same-source/same-path/second matches.

- DNS behavior is broad and often cache-correct. `zeek-core/dns.json` has 2,987 records across A, AAAA, TXT, PTR, SRV, SOA, NS, and MX, with NOERROR, NXDOMAIN, SERVFAIL, and REFUSED outcomes against two resolvers. External cached sequences frequently decrement TTL by elapsed time: `api.snapcraft.io` goes from 1,281 seconds at `12:02:27.862214` to 419 at `12:16:49.367466`, and from 631 at `13:13:17.002872` to 496 at `13:15:32.046958`; `r3.o.lencr.org` goes from 481 at `14:21:52.084538` to 479 two seconds later. Internal authoritative records correctly return fixed zone TTLs rather than cache-decremented values.

- TLS and certificate semantics are strong. `zeek-dmz/ssl.json` has 2,217 established sessions spanning TLS 1.2 and TLS 1.3 with compatible AES-GCM, AES-CBC, and ChaCha20 suites; 705 are resumed and 1,512 are full sessions. Resumed sessions do not carry certificate chains. Every one of 896 DMZ chain FUID references resolves to both `x509.json` and `files.json`; repeated fingerprints preserve certificate metadata; all certificates are valid at observation time; and all 78 OCSP records fall within their `thisUpdate`/`nextUpdate` windows. Core and database sensors show the same invariants.

- Lateral activity has credible network mechanics. At about `13:40:16–13:40:40`, `10.10.3.10` performs an ICMP discovery and five-port TCP sweep of `10.10.2.1–254`. DMZ sees all 254 ICMP targets and all 254 targets on ports 22, 80, 443, and 3306, but 253 on port 445; core misses one different ICMP target while seeing all 254 TCP targets. Response states vary by live host and service. The differences are consistent with independent packet loss rather than cloned sensor output.

- The subsequent SSH lifecycle is correctly ordered and source-native. Zeek DMZ sees `10.10.3.10:54236 -> 10.10.2.30:22` begin at `14:14:36.367958Z`; the ASA builds the connection at `14:14:36`; `APP-INT-01.meridianhcs.local/syslog.log` records the connection at `14:14:40.210662Z`, accepts `root` at `14:14:48.051638Z`, and opens PAM at `14:14:48.097051Z`. Zeek closes at `17:56:58.549217Z`, ASA tears down at `17:56:58` after `3:42:22`, syslog closes PAM at `17:57:00.548000Z`, and endpoint telemetry logs out at `17:57:01.758Z`. This is operationally plausible transport-before-auth and close-before-session-finalization behavior.

- Collection is not artificially perfect. Three application FUID references lack a corresponding `files.json` row: core SMB FUID `FEPJIENeNLjvXCrJBe`, core HTTP FUID `FmfOokDERTjrIpPia3`, and DMZ HTTP FUID `FqAQIx3LH0EbjCiwPq`. Conversely, incomplete certificate files with nonzero `missing_bytes` sometimes have no `x509.json` record. These sparse gaps are compatible with extraction failure or source-local loss and do not contradict the collection profile.
## Detailed Analysis
The visible network window runs from approximately `2024-03-18T12:00:06Z` through `17:59:33Z`. Core traffic is dominated by DNS (2,997 service-tagged connections), Kerberos (2,272), HTTP/proxy (1,678), LDAP (1,162), SMB (414), TLS (363), syslog (324), SSH (52), DHCP (48), SMTP (46), RDP (24), and DCE/RPC (10). The DMZ adds substantial Internet exposure: 777 unique globally routable external addresses appear, with inbound web clients, several distinct scanner populations, and outbound proxy/origin traffic. Database visibility is appropriately narrower and dominated by 342 TCP/3306 connections, of which 334 are identified as MySQL.

Connection states and durations are not uniform. Core has 9,021 `SF`, 2,023 `S0`, 148 `RSTO`, 80 `RSTR`, 25 `OTH`, 22 `REJ`, 18 `S2`, 12 `S3`, and five `S1` records. Of 9,309 core records with duration, values range from `0.000202` to `13,342.181861` seconds, with 8,691 unique duration values. DMZ and DB show similarly varied distributions. Failed scans use plausible SYN-only `S0` forms with IPv4/TCP header sizes of 40, 52, 60, or 64 bytes; successful protocols have varied packet counts, histories, payloads, and reset/FIN behavior.

Traffic volume is mostly steady but includes a defensible scanner burst. Core has at least one connection in every minute and a median of 27 connections per minute; DMZ has a median of 15.5 and seven empty minutes. The outlier minute beginning `13:40:00` contains 1,564 core and 1,549 DMZ connections because of the `/24` discovery/port scan, not because baseline services all spike together. The scan's ICMP phase takes about 3.8 seconds and its five-port TCP phase about 8.2 seconds, which is plausible for a parallel scanner. Other baseline families are irregular: per-source syslog intervals range from seconds to more than an hour, Kerberos/LDAP activity has broad interval variation, and web/proxy sessions arrive in human and service bursts rather than fixed slots.

External activity is also textured. High-volume source `185.70.41.45` first requests `/` at `12:30:10`, then performs Nikto-like HTTPS reconnaissance, SQL injection attempts at `13:00:08` and `13:00:10`, and an upload at `13:20:17`. Its 326 web records align with 325 established TLS observations plus one plaintext HTTP observation, while TLS resumption is mixed (151 resumed, 174 full). Other external sources have distinct profiles: SMB/RDP-focused probes, database-port scans, mixed web/service scans, and ordinary browser-like request bursts. Suspicious behavior is treated here as behavior to validate, not as proof of synthetic origin.

The decisive authenticity question is therefore not whether the activity is easy to reconstruct, but whether source-native mechanics hold. Most do. Firewall connection IDs, NAT allocation, teardown semantics, sensor-specific UIDs, loss accounting, proxy tunnel totals, HTTP bodies, certificate references, TLS cipher/version combinations, cache TTL decay, and SSH lifecycle timing all survive focused checks. The DNS retry byte-accounting defect and the mirrored Snort timing envelopes are the two findings with the highest synthetic weight because they expose how events appear to have been constructed rather than merely what story they tell.

No finding relies on directory timestamps, external DNS resolution, missing Sysmon event types, completeness of correlation, narrative neatness, or thin coverage by itself. No hard contradiction was established; the verdict is probabilistic and driven by repeated implementation-like texture embedded in otherwise highly realistic telemetry.

## Recommendations
1. Correct UDP DNS retry accounting. When a query or response is retransmitted, add the retransmitted DNS payload to `orig_bytes`/`resp_bytes` and IP totals, and ensure the DNS transaction representation matches the intended source-native behavior. If the second datagram is intentionally empty, do not present it as a payload-bearing `D`/`d` history event. Add regression checks covering both originator retries and duplicate responses.

2. Timestamp IDS alerts from the triggering packet's capture time, then apply only a stable sensor-clock model (with realistic slow drift if desired). Do not add a fresh approximately 0.2–0.3 second processing delay to fast-log timestamps. Validate DNS-query alerts specifically, because the triggering packet is unambiguous, and compare adjacent events to ensure sensor offset is temporally autocorrelated rather than independently sampled.

3. Broaden certificate ecology. Reuse some leaf certificates across related SNI values; include realistic wildcard and multi-SAN certificates for CDN/SaaS families; preserve occasional CN/SNI non-identity where SAN validation is authoritative; and model OCSP validity windows as issuer-policy distributions rather than largely per-certificate random windows.

4. If these are intended as raw Zeek logs, preserve logger emission order, particularly for long-lived `conn.log` records. If they are intentionally normalized SIEM exports, make that provenance explicit in the review dataset so strict `ts` sorting is not mistaken for source-native ordering.

5. Retain the current firewall/NAT state model, source-local packet loss, proxy byte contracts, TLS resumption/chain behavior, DNS cache decay, web static/dynamic size behavior, and SSH lifecycle ordering. These are the strongest authenticity features and should be protected with regression tests while the higher-impact artifacts are corrected.
