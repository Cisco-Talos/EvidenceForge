# Host/EDR Forensics Analyst — Authenticity Assessment

## Verdict

**Assessment:** Synthetic
**Verdict Confidence:** 82
**Synthetic-Confidence Score:** 66

## Executive Summary

The endpoint telemetry is unusually strong in process identity, hash stability, ordinary process-tree semantics, and Windows/Linux/network timing, but three concrete defect families outweigh that realism. Two Windows lock/unlock lifecycles are physically implausible and detached from their Type 7 logons, eCAR repeatedly classifies the executable `crashpad_handler.exe` as a loaded module, and seven in-window SSH sessions retain only close-side syslog evidence despite contemporaneous eCAR proving that their transport, login, and server process started inside the visible window.

## Evidence For Synthetic

- [hard_contradiction] Two of the six visible Windows lock/unlock pairs occur effectively instantaneously. In `WS-AJOHNSON-01.meridianhcs.local/windows_event_security.xml`, Event 4800 at `2024-03-18T17:47:57.257802Z` is followed by Event 4801 only `0.000218` seconds later for Logon ID `0x2721d61`; the only Type 7 Event 4624 for that session is at `17:34:38.319633Z`, `798.938387` seconds earlier. In `WS-MCHEN-01.meridianhcs.local/windows_event_security.xml`, Events 4800/4801 at `15:50:29.451650Z` and `15:50:29.452803Z` are `0.001153` seconds apart, while the nearest Type 7 logon is at `15:42:38.421280Z`, `471.031523` seconds earlier. A human cannot authenticate and unlock in 0.218–1.153 ms, and the expected Type 7 companion is not temporally attached to either 4801.
- [schema_or_format] Six eCAR `MODULE/LOAD` records on four workstations identify `crashpad_handler.exe` as a module loaded into `GoogleDriveFS.exe`. Examples are `WS-DRAMIREZ-01.meridianhcs.local/ecar.json` at epoch-ms `1710765691939` (PID `6436`) and `1710773014184` (PID `6764`), `WS-EBROOKS-01.meridianhcs.local/ecar.json` at `1710767513640` and `1710777078785`, `WS-SMARTINEZ-01.meridianhcs.local/ecar.json` at `1710780222473`, and `WS-AJOHNSON-01.meridianhcs.local/ecar.json` at `1710780233145`. The path is consistently `C:\Program Files\Google\Drive File Stream\97.0.1.0\crashpad_handler.exe`. Crashpad handler is a helper executable that should be represented as a spawned process, not a DLL-style module load; no corresponding `PROCESS/CREATE`, Security 4688, or Sysmon Event 1 for `crashpad_handler.exe` appears anywhere in the reviewed data.
- [contract_gap] Seven successful SSH sessions created after the collection began have no same-PID `Connection from`, `Accepted`, or `pam_unix(...): session opened` lines in their host syslog; each retains only `session closed`. This affects 7 of 59 visible eCAR SSH child-process creations across six hosts: PID `2984080` on APP-INT-01, `1072587` on DB-PROD-01, PIDs `687997` and `722135` on LOG-MON-01, `462746` on MAIL-CLIN-01, `2008095` on MAIL-EDGE-01, and `2707544` on WEB-EXT-01. For example, `APP-INT-01.meridianhcs.local/ecar.json` shows inbound TCP/22 from `10.10.4.10:44375` at `1710782183302`, `sshd: root [priv]` PID `2984080` created at `1710782188180`, and successful session `378793` at `1710782189620`; `APP-INT-01.meridianhcs.local/syslog.log` contains only the close at `2024-03-18T17:16:57.685746Z` and the subsequent `systemd-logind` removal. This is not a pre-window-session issue.
- [contract_gap] The same APP-INT-01 SSH transfer assigns a file creation directly to the privileged monitor identity. At epoch-ms `1710782218241`, eCAR attributes creation of `/tmp/.cache/rpt_0318.sql.gz` to the same process object/PID `2984080` that was created as `sshd: root [priv]`, while changing its command line to `sshd: root@notty`. Modern OpenSSH privilege separation uses a distinct session-side child (or an `sftp-server`/`scp` process) for user-context transfer work; the privileged monitor should not silently become the file-writing session process under the same identity.
- [distribution_texture] All 987 Sysmon Event 1/Security 4688 pairs across the ten Windows hosts place Sysmon first and Security second, with lags restricted to `35.306–898.552 ms` (median `137.569 ms`). Provider ordering can favor Sysmon, so this is not a contradiction and complete matching was not scored by itself; the universally one-direction, tightly bounded lag nevertheless adds a modest generated-timing texture when combined with the harder findings.

## Evidence For Real

- The process lifecycle graph is internally strong. Across all ten Windows Sysmon files, 987 Event 1 process creations showed no visible parent ProcessGUID created after its child, no self-parenting, no reused ProcessGUID, and no Event 5 termination before the matching Event 1. Across all 21 eCAR host files, no process object with both CREATE and TERMINATE evidence terminated before creation.
- Windows process trees are source-plausible and role-sensitive rather than generic. Recurrent chains include `smss.exe → winlogon.exe → userinit.exe → explorer.exe`, `csrss.exe → conhost.exe`, `services.exe → service binary`, and `searchindexer.exe → searchprotocolhost.exe/searchfilterhost.exe`. Workstations also differentiate user software: Chrome/Edge and VPN/Google Drive on WS-DRAMIREZ-01, Postman/Slack/VPN tooling on WS-PPATEL-01, and administrative PowerShell/SSH/RDP activity on WS-MCHEN-01 and WS-AJOHNSON-01.
- Hash handling is convincing. Every image path is hash-stable within each host during the six-hour window; no algorithm value is reused by unrelated binaries, and apparent cross-path matches are the same per-user-installed product (for example Teams or Slack under different user profiles). Core Windows binaries form coherent host cohorts rather than changing hashes between executions.
- Security 4688 and Sysmon Event 1 agree on PID and image for all 987 Sysmon process creations within two seconds. The field forms are native-looking: hexadecimal Security PIDs, decimal Sysmon PIDs, host-stable Sysmon ProcessGUID prefixes with time-bearing components, full four-algorithm hash strings, and appropriate parent GUID/image/command-line data.
- Most session lifecycles are credible. Four of the six Windows lock/unlock pairs last `182.272`, `355.813`, `499.699`, and `2184.799` seconds and have their Type 7 Event 4624 within `0.213–0.511` seconds of Event 4801. Network logons generally close after short service-style durations, while interactive/RDP sessions persist much longer; no shared Logon ID has a visible logoff before its first visible logon.
- SSH transport and endpoint evidence often align naturally. For `10.10.1.31:60669 → 10.10.2.21:22`, WS-MCHEN-01 eCAR records the client flow at epoch-ms `1710773426309`; Zeek records connection start `1710773426.585390`; FILE-LNX-01 eCAR records inbound flow at `1710773429047` and login at `1710773438432`; syslog records connection at `14:50:30.506915Z`, accepted password at `14:50:37.110368Z`, and session open at `14:50:37.198262Z`. The client process remains alive until after the Zeek transport closes, and the endpoint session closes coherently.
- Linux telemetry has substantial lived-in texture: RFC 5424-style priority/facility values, long-lived daemon PIDs mixed with steadily advancing transient PIDs, paired sudo PAM opens/closes, sysstat cron executions with small launch jitter, DHCP renewals, NetworkManager transitions, package/update activity, logind session IDs, snapd state changes, and varied bash histories. Across 317 bash commands in 22 history files, no three-command-or-longer sequence repeats between histories.
- Native Windows lifecycle details are handled well. On DC-01, Event 1102 at `2024-03-18T17:42:34.140397Z` uses the `Microsoft-Windows-Eventlog` provider, stores subject identity under `UserData/LogFileCleared`, resets `EventRecordID` to `1`, and is followed by post-clear record IDs. The account lifecycle for `svc_dirsync` also maintains one SID through Events 4720, 4724, 4738, 4728, and 4726 in plausible order.

## Detailed Analysis

The reviewed data covers approximately `2024-03-18 12:00–18:00 UTC` and contains 34,620 eCAR records from 21 hosts, 19,355 Security events and 12,118 Sysmon events from ten Windows hosts, 3,756 syslog lines from eleven Linux hosts, and 317 timestamped commands across 22 bash-history files. Three Zeek sensor directories provide transport evidence. Filesystem timestamps and directory naming were not used as authenticity evidence.

Process creation and termination semantics are the strongest part of the collection. The ten Sysmon files contain 987 process creates with unique ProcessGUIDs, valid visible parent ordering, and sensible parent/child families. Security 4688 mirrors those process starts without PID/image disagreement. Process runtimes are not quantized: for example, 145 `taskhostw.exe` lifetimes are all unique to the millisecond, 116 `wmiprvse.exe` lifetimes are all unique, and 19 `ssh.exe` lifetimes vary from `306.096` to `3449.801` seconds. This avoids a common synthetic fingerprint of fixed durations.

Hash behavior also argues for production-like telemetry. Frequently repeated files such as `taskhostw.exe`, `WmiPrvSE.exe`, `conhost.exe`, and `dllhost.exe` retain one hash set per host. Cross-host variants cluster consistently by fleet cohort, which is compatible with different Windows servicing levels. The exception is not cryptographic instability but object semantics: eCAR treats `crashpad_handler.exe` as a module in six Google Drive executions. That repeated category error is difficult to explain as ordinary collection variance because it reproduces the same incorrect relationship on four independent endpoints.

Windows logon IDs and session durations are generally coherent. Repeated 4624 records for the same interactive LUID are attributable to workstation unlock Type 7 events rather than accidental duplicate interactive sessions. The normal lock/unlock examples establish the expected local contract: Type 7 appears a few hundred milliseconds before Event 4801. Against that baseline, the AJOHNSON and middle MCHEN cycles are clear outliers: both place 4801 within roughly one millisecond of 4800 and hundreds of seconds after Type 7. Those are not merely incomplete lifecycles; their visible ordering and elapsed times conflict with the semantics of an authenticated workstation unlock.

Linux session construction is mostly detailed and coherent. Successful SSH sessions normally show transport, an `sshd` child, accepted authentication, PAM session open, logind session allocation, shell activity, PAM close, and logind removal. Failed sessions use plausible pre-auth forms. However, seven eCAR-proven in-window successful sessions lose the entire open side only in syslog while retaining the close side. Because eCAR shows that each associated `sshd` process was created after 12:00 and the affected syslog files were already collecting records, bounded-window truncation cannot account for these seven cases. Random production loss remains possible, but the same lifecycle-shaped omission across six hosts is a material contract gap.

Endpoint/network consistency is otherwise notably good. SSH client processes precede their flows, target flow observations precede authentication, and client/target session termination fits Zeek connection duration. Windows RDP and remote-administration process trees use plausible client and service processes. eCAR identities remain stable from process creation through dependent module/file/flow actions and termination. This coherence was treated as realism evidence only; its completeness was not used as a synthetic clue.

The background environment is differentiated by host role: domain controllers carry Kerberos and WFP-heavy activity, FILE-LNX-01 carries Samba audit records, WEB-EXT-01 has web service traffic, PROXY-01 has proxy activity, and endpoint software differs among users. Linux syslog contains diverse daemon and maintenance behavior instead of only attack-related rows. Some baseline families recur heavily—across Windows hosts, `taskhostw.exe`, `WmiPrvSE.exe`, `conhost.exe`, and `dllhost.exe` account for 470 of 987 Sysmon process creations—but the individual timing, lifetime, command-line, and host-cohort details are varied enough that this did not independently drive the verdict.

## Realism Score by Category

- **Field format accuracy:** 7 — Windows XML, Sysmon fields, hashes, GUIDs, and RFC 5424 syslog are strong, but the repeated executable-as-module classification is a material native-semantics defect.
- **Temporal patterns:** 6 — Most process and session durations are varied and causal, but two sub-1.2-ms lock/unlock cycles are not physically credible.
- **Cross-source correlation:** 7 — Process and flow correlation is excellent and causally ordered, offset by seven repeated SSH open-side syslog gaps and one incorrect SSH file-owner process.
- **Behavioral realism:** 8 — User software, administration, service activity, bash commands, and endpoint lifetimes are varied and role-sensitive.
- **Environmental consistency:** 8 — Host roles and background services agree well across the estate, with no broad OS/path or service-placement contradiction found.

## Recommendations

- If this were synthetic, generate Events 4800, Type 7 4624, and 4801 from one session-lock lifecycle. Enforce a human-scale locked interval and require Type 7 to precede 4801 by the normal provider delay; never emit an independent 4800/4801 pair within milliseconds.
- Model Crashpad as a child executable process with its own PID/process identity and parent `GoogleDriveFS.exe`. Remove `.exe` paths from module-load catalogs unless there is explicit evidence of an executable image being mapped as a module, and add a source-native validation rule for this case.
- Make syslog observation decisions atomic for each SSH lifecycle. A retained close for an in-window session should normally retain the same-PID connection/auth/PAM-open sequence, or the collection should expose a plausible source outage covering the missing rows rather than dropping only the open side across multiple hosts.
- For SCP/SFTP transfers, preserve OpenSSH privilege-separation identities. Keep the `[priv]` monitor distinct from the user-context `user@notty`, `internal-sftp`, `sftp-server`, or `scp` child, and attribute file creation to the process that actually writes the file.
- Retain the existing per-host hash stability, process GUID behavior, varied runtimes, role-specific software, and transport-before-auth ordering; these are the strongest production-like features in the dataset.
