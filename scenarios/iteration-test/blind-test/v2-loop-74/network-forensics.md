# Network Forensics Analyst — Authenticity Assessment
## Verdict
**Assessment:** Synthetic
**Verdict Confidence:** 90
**Synthetic-Confidence Score:** 84
## Executive Summary
The network evidence is unusually strong at the individual-record level, but repeated cross-source accounting contradictions and highly quantized client timing make the collection more consistent with synthetic construction than sanitized production capture. The decisive issue is not completeness: on inspected proxy tunnels, explicit proxy byte totals and Zeek transport payload totals disagree by hundreds of kilobytes on the exact same client/proxy tuple, despite zero `missed_bytes`. The proxy's own per-transaction rows exactly reconcile to its tunnel totals, which removes ordinary log-loss or ambiguous aggregation as a convincing explanation for the largest cases.

The collection otherwise models Zeek semantics well. Across 20,495 `conn.json` records, packet/IP-byte arithmetic, connection-state behavior, protocol numbers, locality flags, UID uniqueness, and child-analyzer timing are coherent. DNS, TLS/X.509, ASA lifecycle, IDS tuple matching, realistic sensor clock offsets, and sensor-specific packet loss all provide substantial evidence for authenticity. Those strengths prevent a higher score, but they do not overcome the repeated proxy transport contradictions, 600 ms scheduling texture, and smaller analyzer-contract gaps. Filesystem timestamps and domain reputation or ownership were not used.
## Evidence For Synthetic
- **hard_contradiction — inspected proxy byte accounting does not fit the observed TCP payload.** `PROXY-01.meridianhcs.local/proxy_access.log` contains 720 inspected tunnel IDs whose non-CONNECT `cs_bytes`/`sc_bytes` sums exactly equal the CONNECT row's `tunnel_cs_bytes`/`tunnel_sc_bytes`. Nevertheless, 430 of 719 inspected CONNECTs matched to Zeek differ from `cs_bytes + tunnel_cs_bytes` or `sc_bytes + tunnel_sc_bytes`; 118 exceed a generous 5% plus 2 KiB allowance. At 2024-03-18 15:33:46 UTC, tunnel `PT-b8882fb4c111f8ca` declares `sc_bytes=226` and `tunnel_sc_bytes=156588`, while `zeek-core/conn.json` UID `CqxDm2DrpeoRDlICa2` at `1710776026.685242` records `resp_bytes=793756`, `missed_bytes=0`: 636,942 response payload bytes are unexplained. The same row declares `cs_bytes=225`, `tunnel_cs_bytes=644`, versus Zeek `orig_bytes=4453`, an unexplained 3,584 bytes.
- **hard_contradiction — the mismatch is repeated and sometimes extreme.** At 2024-03-18 12:10:31 UTC, `PT-c2b640af6bcf35c1` reports `sc_bytes=216`, `tunnel_sc_bytes=46707`; `zeek-core/conn.json` UID `C0uvPzvgr4k4RgIdGD` at `1710763830.955345` has `resp_bytes=647968`, `missed_bytes=0`, a 601,045-byte excess. At 12:10:17, `PT-abd8e632622da430` reports 65,809 total server-to-client bytes while UID `CEod6zGZfuSRznxzQn` has 571,707, again with no missed bytes. TLS record framing and HTTP headers cannot plausibly account for factors of roughly 5 to 14, and the proxy rows for each tunnel already reconcile internally.
- **distribution_texture — repeated 600 ms client fan-out.** In `zeek-core/conn.json`, 177 of 1,583 adjacent per-client connections to `10.10.3.20:8080` begin within 0.597-0.603 seconds of one another, spanning eight client addresses; `zeek-dmz/conn.json` independently observes the same underlying pattern. For `10.10.1.21`, UIDs `CDkSXZDJeHFRqbCqiW`, `CcdXfPRfetuHjpjzBRh`, `CCPqGSwYZ3b1AlDC5IR`, and `Cjgsjg6Tf301mDiuKe` begin at 2024-03-18 13:40:25.934009, 13:40:26.534656, 13:40:27.133496, and 13:40:27.733895 UTC. The texture also occurs within persistent HTTP connections: 21 of 54 intra-UID transaction gaps in `zeek-core/http.json` are 0.600 seconds within 3 ms. UID `CEZdlcR1E3zIuLW1WE` has four consecutive asset requests separated by almost exactly 0.600 seconds from 13:56:45.367630 through 13:56:47.767628 UTC. This much cross-host quantization is atypical of browser, scheduler, and network jitter.
- **contract_gap — IDS asserts HTTP CONNECT where Zeek sees no HTTP analyzer.** All five `ET POLICY HTTP CONNECT Tunnel Attempt Inbound` alerts have a matching bidirectional Zeek TCP flow on port 8080, but none has `service:"http"` or an `http.json` row. For example, `snort-core/snort_alert.log` at `03/18-16:08:09.659541` identifies `10.10.2.21:45300 -> 34.104.147.54:8080`; `zeek-core/conn.json` UID `CLQicgwJOmtdLQMc1A` starts at `1710778089.425684`, has `orig_bytes=1746`, `resp_bytes=574`, and `missed_bytes=0`, yet no HTTP service. The perimeter example at `03/18-12:49:22.937634` maps to `zeek-dmz/conn.json` UID `C4O2dErM3P50qmzZJi` with `181/881` payload bytes and `missed_bytes=0`, again without HTTP. A signature based on parsed CONNECT semantics and a Zeek port-8080 flow with intact bidirectional payload should normally leave compatible analyzer evidence.
- **contract_gap — certificate and file references are occasionally orphaned.** Thirty-nine established, non-resumed TLS 1.2 records have an `X` certificate marker in `ssl_history` but no `cert_chain_fuids`: four in `zeek-core/ssl.json`, 34 in `zeek-dmz/ssl.json`, and one in `zeek-db/ssl.json`. One example is `zeek-core/ssl.json` UID `C39O6DGGRR9AneEUo` at `1710772834.471742`, with `TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384`, `resumed=false`, `established=true`, and `ssl_history="CSXKNGIFIFT"`. Separately, seven of 838 HTTP/SMTP FUID references have no `files.json` row. The most conspicuous is `zeek-dmz/http.json` UID `CDU5GwyLG87xsqCnmbV` at `1710780779.299608`: a 137,247,004-byte MSI response references `Fgtt3hzSHorOC53d6n`, but that FUID is absent from `zeek-dmz/files.json` despite `missed_bytes=0` on the 137,247,200-byte connection.
## Evidence For Real
- **schema_or_format — core Zeek connection semantics are strong.** The three sensors contain 20,495 connection records. No record has negative payload/IP-byte accounting, bytes with zero packets, an invalid port, an IP-protocol mismatch, or an incorrect `local_orig`/`local_resp` designation for the observed 10/8 environment. Every S0 flow has zero responder packets/bytes, every REJ has responder evidence, and the only missing durations are exactly the 4,650 S0/REJ records where Zeek commonly leaves duration unset.
- **schema_or_format — UID/FUID and analyzer timing are mostly source-native.** All 3,959 DNS, 3,704 HTTP, 2,628 TLS, and 46 SMTP rows have a same-sensor `conn.json` UID. All child analyzer timestamps fall within their parent connection interval, and all 2,097 file records finish within a referenced connection interval. All 1,083 TLS certificate FUID references resolve in both `files.json` and `x509.json`; repeated fingerprints have stable serial, subject, issuer, validity, key, SAN, and CA metadata.
- **environment_or_collection_plausibility — independent sensor observations look credible.** There are 4,221 unambiguous core/DMZ observations of the same five-tuple. DMZ timestamps precede core timestamps by 110-118 ms with a median 114 ms, consistent with stable clock offset plus drift. Approximately 10% differ in packet or byte totals/history, and every nonzero `missed_bytes` value has the corresponding Zeek `G/g` gap marker; this is credible vantage-specific capture loss rather than blind duplication.
- **schema_or_format — firewall lifecycle is internally consistent.** `fw-perimeter/cisco_asa.log` contains 7,431 built TCP/UDP connections and 7,430 teardowns. The sole unmatched build is an SSH flow created at 17:31:19, still plausibly active when the six-hour window ends. Every matched teardown's integer duration agrees with its build/teardown timestamps to 0 or 1 second, all 1,876 dynamic translations have a matching teardown, and connection IDs increase monotonically by one without reuse.
- **cross-source correlation — IDS alerts agree with network facts where semantics are directly testable.** All 152 port-bearing Snort-style alerts parsed from the two alert files have a same-tuple Zeek connection within one second. Every DNS-TLD alert maps to a DNS query with the stated suffix. The alert mix—DNS policy, STUN, BitTorrent, scanning, JA3, package-management, curl, and basic-auth policy—has realistic benign/malicious variety instead of one signature family dominating everything.
- **behavioral realism — protocol and state distributions are plausible.** Core traffic includes DNS, Kerberos over UDP and TCP, LDAP, SMB, proxy HTTP, TLS, syslog, SMTP, SSH, RDP, DHCP, and ICMP. The DMZ shows public HTTPS scanning, outbound proxy/TLS, internal web access, and application-to-MySQL traffic; the DB vantage is appropriately dominated by 304 MySQL-analyzed connections. The 13:40 UTC burst is a recognizable high-speed scan from `10.10.3.10` across 255 targets and six principal probe types, with 1,483 S0 results plus a small number of SF/REJ/reset outcomes, rather than an implausibly uniform baseline surge.
- **schema_or_format — DNS and PKI details are unusually careful.** No NXDOMAIN response carries answers, A/AAAA answers match their declared families, answer and TTL counts agree, and internal authoritative TTLs use sensible fixed values. TLS version/cipher combinations are valid; no resumed session carries a new certificate chain; certificate issuer/subject links are intact; and every observed certificate is valid at its observation time.
## Detailed Analysis
The collection spans approximately 12:00-18:00 UTC on 2024-03-18. `zeek-core/conn.json` has 11,712 records, `zeek-dmz/conn.json` 8,345, and `zeek-db/conn.json` 438. Core states are 9,446 SF, 1,954 S0, 123 RSTO, 86 RSTR, 35 OTH, 30 REJ, and small S1-S3 populations. DMZ states are 5,498 SF, 2,620 S0, 99 RSTO, 61 RSTR, 30 REJ, and small partial-state populations. These distributions, including unanswered scan traffic and asymmetric resets, are credible.

Packet and byte semantics are particularly convincing. UDP and ICMP IP-byte deltas consistently reflect IPv4 plus transport/control overhead, while TCP overhead varies with packet count and options. Large downloads also preserve ACK behavior: `zeek-dmz/conn.json` UID `CDU5GwyLG87xsqCnmbV` transfers 137,247,200 responder payload bytes in 94,243 responder packets while the origin sends 47,003 mostly ACK-only packets carrying only 384 payload bytes. HTTP body totals never exceed the parent connection's observed payload plus declared `missed_bytes`. This makes the separate inspected-proxy accounting failures more salient: the low-level model is coherent until two independently populated accounting views must agree.

The proxy evidence is the strongest discriminator. Opaque tunnel accounting is often exact, and every inspected tunnel's transaction aggregate exactly matches its own declared tunnel totals. Therefore the hundreds-of-kilobytes excesses in Zeek are not random parser noise. They show two incompatible byte models attached to the same flow. The 118 gross cases are distributed across multiple users, times, and destinations, so they are not an isolated damaged record. This is assessed as a repeated hard contradiction, with the caveat that an undocumented proxy policy that transforms responses or suppresses transaction rows could reduce its weight; the exact tunnel aggregates and zero-loss Zeek examples make that caveat unlikely to explain the largest discrepancies.

Temporal behavior is mixed. Broad traffic volume varies credibly, including a 1,580-record core minute during the 13:40 scan, normal quieter minutes, long SSH sessions up to about 3.7 hours, short DNS RTTs, and varied application durations. Conversely, the repeated 600 ms fan-out appears at both connection and HTTP-transaction layers and across eight clients. Because the same underlying packets are seen by core and DMZ, cross-sensor duplication was not counted as independent evidence; the indicator is the repeated source behavior itself.

DNS is one of the strongest production-like families. Core contains 2,969 DNS transactions, DMZ 947, and DB 43. The mix includes A, AAAA, TXT, PTR, SRV, MX, NS, and SOA; NOERROR, NXDOMAIN, SERVFAIL, and REFUSED are used coherently. External TTLs show countdown-like variation and common low values, while authoritative internal records cluster at 300, 600, 1,800, 3,600, 7,200, and 86,400 seconds. A-before-AAAA pairs are consistently sub-second, but their delays vary from roughly 78 to 839 ms, so this was not treated as a decisive synthetic indicator.

TLS and certificate handling is also mostly persuasive. The collection has a plausible TLS 1.2/1.3 mix, valid cipher pairing, session resumption without fresh chains, repeated certificate fingerprints with invariant metadata, and clean issuer-to-subject links. The 39 TLS 1.2 rows with `X` history but no chain are a real contract gap, not a complaint about sparse coverage: those rows affirm that a certificate message was observed and that the handshake completed without resumption. Their broad distribution makes deliberate per-source omission less convincing, though parser or log-filter loss remains possible.

Firewall and IDS records support the modeled network. ASA connection and translation lifecycles are arithmetically correct, and the single open SSH connection is reasonable bounded-window state. Snort-style DNS signatures agree with the actual queried suffixes, and every port-bearing alert has a timely Zeek tuple. The five CONNECT-alert/analyzer disagreements are narrower than the proxy byte issue because independent analyzers can disagree, but four flows have no packet loss and enough bidirectional payload for Zeek's HTTP analyzer on port 8080, so the repeated absence remains suspicious.

## Recommendations
1. Make client-side proxy transport bytes and proxy tunnel counters share one accounting contract. For each CONNECT tuple, define whether `tunnel_cs_bytes`/`tunnel_sc_bytes` are wire payload, decrypted HTTP entity bytes, or upstream-leg bytes; then calculate Zeek `orig_bytes`/`resp_bytes` from that same truth with explicit TLS/control overhead. Add invariants for inspected tunnels, including the large zero-loss examples above.
2. Replace fixed 600 ms browser and proxy fan-out steps with per-client scheduling that reflects browser concurrency, connection pooling, DNS/cache state, response completion, and wider jitter. Verify distributions at both connection-start and intra-connection HTTP transaction levels.
3. Align IDS and Zeek analyzer provenance. If a rule fires on an HTTP CONNECT method over port 8080 and the flow has intact bidirectional payload, emit compatible Zeek `service="http"` and `http.json` evidence. If modeling analyzer failure, supply a concrete reason such as packet loss, truncation, midstream capture, or deliberate analyzer disablement rather than leaving five clean flows unexplained.
4. When TLS 1.2 `ssl_history` contains `X` on an established, non-resumed ECDHE certificate handshake, create the corresponding certificate FUID/files/X.509 records or model an explicit parse/log-drop condition. Likewise, do not leave a directly referenced HTTP FUID absent—especially for a 137 MB MSI on a zero-loss flow—unless the collection profile visibly explains that omission.
5. Preserve the strongest existing realism: state/history semantics, packet/IP-byte arithmetic, cross-sensor clock offset and loss variation, ASA lifecycle math, DNS response logic, certificate reuse, and bounded-window handling should remain regression contracts.
