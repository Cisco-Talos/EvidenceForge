# Loop 84 family contract — Windows Kerberos TGT/TGS source order

- **Owning abstraction:** `SourceTimingPlanner` and the canonical Windows KDC audit action bundle. The Windows emitter owns XML serialization; it cannot repair rows after source timing has been frozen.
- **Invariant:** when a modeled Kerberos exchange contains an observable TGT (4768) and a dependent service ticket (4769) on the same client/DC/transport transaction, the final Security timestamps preserve TGT-before-TGS order with a positive, bounded gap. Independent transactions and out-of-window cached TGTs must not be falsely paired.
- **Entry paths:** (1) `KerberosConnectionAuditActionBundle` emits transport-bound KDC TGT/TGS companions; (2) `KerberosLogonTicketsActionBundle` emits the pair supporting a member-host logon; (3) direct TGT/service-ticket action bundles serve baseline and other causal callers; (4) cached-TGT service tickets may have no visible TGT and must remain valid.
- **Consumer inventory:** Windows Security 4768/4769 source timing and renderers; machine-logon-after-service-ticket planning; WFP/KDC transport ordering; Windows XML/Snare output; evaluation and the loop84 Kerberos ordering probe.
- **Layer rationale:** the source timestamp becomes immutable in `SourceTimingPlan`; existing emitter repair explicitly skips finalized rows. The canonical planner sees the transaction ID, tuple, account, event type, and source clock and can preserve causality before rendering. Emitter-only timestamp edits would create a split between the frozen plan and rendered event.
- **Sibling risks:** keep both KDC records within their WFP transport window; preserve cross-host DC/member logon ordering; do not require an in-window TGT for cached-ticket service requests; key dependencies by exact transaction/account identity rather than only user and proximity; maintain checkpoint bounds and deterministic scope.
