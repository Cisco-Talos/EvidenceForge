# Detection Engineer — Authenticity Assessment
## Verdict
**Assessment:** Inconclusive
**Verdict Confidence:** 82
**Synthetic-Confidence Score:** 43
## Executive Summary
The records are highly production-like in schema, source-specific precision, identity handling, lifecycle behavior, and cross-source causal order. Windows Security and Sysmon metadata match their native providers and event versions; Zeek UIDs, tuples, protocol companions, certificate chains, packet accounting, and sensor-specific clock offsets are coherent; eCAR process and session object lifecycles do not visibly invert; and Linux, proxy, firewall, web, and shell-history records use plausible native formats. A representative 20-record review was supplemented by aggregate checks over the available Windows XML and JSON-line telemetry.

Two concrete defects prevent a Real verdict. First, one Security 4800/4801 pair locks and unlocks the same workstation session only 0.000406 seconds apart, which is not a plausible user lock interval. Second, Sysmon Event ID 1 repeatedly supplies four complete hashes while replacing all five PE version-resource fields with `-` for stable, well-known installed executables; this is repeated rather than an isolated collection miss. The rest of the corpus contains substantial evidence against a simplistic generator: bounded-window lifecycle edges, selective source gaps, distinct Zeek sensor UIDs and clock skews, nonzero packet loss, varied connection states, and internally correct Windows record-ID reset behavior after a Security-log clear.

The balance is therefore mixed but leans production-like. The synthetic-confidence score is just above the inconclusive threshold because the lock/unlock interval is a hard visible contradiction and the PE-enrichment gap recurs across hosts; completeness or narrative cleanliness was not counted as evidence.

## Evidence For Synthetic
- **[hard_contradiction] Sub-millisecond lock/unlock lifecycle.** In `WS-AJOHNSON-01.meridianhcs.local/windows_event_security.xml`, Event ID 4800 at `2024-03-18T17:44:18.6910419Z` (record 131203) is followed by Event ID 4801 at `2024-03-18T17:44:18.6914477Z` (record 131204). Both identify SID `S-1-5-21-1524654518-2022274387-1755902678-1007`, user `aisha.johnson`, LogonID `0x269710a`, and SessionId `2`. A 406-microsecond locked state cannot represent a human unlock and is the strongest authenticity defect. Other lock intervals are realistic—176.626 and 2,952.875 seconds on `WS-DRAMIREZ-01`, and 488.532 and 2,031.269 seconds on `WS-MCHEN-01`—which makes this a one-off defect rather than a dataset-wide timing model.

- **[schema_or_format] Repeated blank PE metadata despite successful hashing.** Sysmon Event ID 1 records for `C:\Program Files (x86)\Google\Update\GoogleUpdater.exe` contain `FileVersion`, `Description`, `Product`, `Company`, and `OriginalFileName` all set to `-`, while still reporting SHA1, MD5, SHA256, and IMPHASH. This occurs in all 23 observed executions: nine on `WS-AJOHNSON-01`, six on `WS-EBROOKS-01`, and eight on `WS-PPATEL-01`. One concrete example is `WS-AJOHNSON-01.meridianhcs.local/windows_event_sysmon.xml` at `2024-03-18T12:04:59.3005231Z`, record 30309, PID 5184, hash set beginning `SHA1=074E1DA6...` and `SHA256=D1692A59...`. The same all-placeholder pattern appears in all 12 observed `C:\Windows\System32\MpCmdRun.exe` process creations across the Windows hosts, again usually with complete hashes. Transient enrichment failure is possible, but deterministic all-or-nothing treatment of recurring installed binaries is less production-like.

- **[weak_signal] Very tightly bounded provider-delay texture.** Across 964 same-PID/same-image process creations matched between Security 4688 and Sysmon 1, Sysmon always precedes Security by 35–646 ms, with per-host medians clustered between 111 and 155 ms. Consistent provider ordering is normal and this is not a contradiction, but the uniformly bounded shape across ten hosts is slightly mechanical. It receives little score weight because it can also arise from stable same-host provider pipelines.

## Evidence For Real
- **Native Windows schemas are unusually accurate.** Security records use the expected provider GUID `{54849625-5478-4994-a5ba-3e3b0328c30d}`, versions, tasks, keyword masks, hexadecimal IDs, SIDs, and insertion-string codes. Examples include 4624 v2/task 12544, 4688 v2/task 13312, 5156 v1/task 12810, 4768/task 14339, and failure-keyword `0x8010000000000000` on 4625/4771. Sysmon records use provider GUID `{5770385f-c22a-43e0-bf4c-06f5698ffbd9}` and plausible schema versions: Event 1 v5, Event 3 v5, Event 5 v3, Event 7 v3, Event 8 v2, Event 10 v3, Event 11 v2, Event 13 v2, and Event 22 v5.

- **Security-log clearing has correct source-native structure.** In `DC-01.meridianhcs.local/windows_event_security.xml`, Event 1102 at `2024-03-18T17:42:06.2498202Z` switches provider to `Microsoft-Windows-Eventlog` with GUID `{fc65ddd8-d6ef-4962-83d5-6e5cfe9ce148}`, uses a namespaced `UserData/LogFileCleared` body, identifies SYSTEM/`0x3e7`, and resets EventRecordID from 28261026 to 1. The next retained Security event has record ID 5, consistent with omitted intervening event types in a selected export.

- **Windows process identity and timing correlate without impossible order.** All 964 matchable Security 4688/Sysmon 1 pairs have identical PIDs and image paths; no image mismatch was found. Likewise, all matchable 4689/Sysmon 5 terminations agree on PID and image. Across all ten Sysmon files there are no duplicate visible ProcessGuids, no termination preceding a visible creation for the same ProcessGuid, and no child whose visibly logged parent is created later. Sysmon GUID texture is also internally credible: the per-host prefix is stable and the middle GUID words encode process-start epoch time rather than behaving as generic random UUIDs.

- **Session lifecycle behavior respects the visible window.** On `DC-01`, 137 of 140 Type 3 logons have matching 4634 records, all five Type 10 logons have matching logoffs, and the three unmatched Type 3 sessions lie at collection edges; 135 Type 5 service logons remain long-lived. `DC-02` similarly pairs 109/111 Type 3 and 4/4 Type 10 sessions. No same-LogonID 4634 precedes its visible 4624, and no paired session lasts under one second.

- **Account and persistence records use coherent Windows semantics.** On `DC-01`, SYSTEM creates `svc_dirsync` in Event 4720 at `16:14:57.1360910Z`, sets its password in 4724 at `16:14:58.8288990Z`, changes UAC state in 4738 at `16:14:59.3056071Z`, and adds SID `...-9101` to Domain Admins in 4728 at `16:15:01.7675173Z`. The process evidence begins earlier with `cmd.exe /c net user ... /add /domain` at `16:14:53.223Z`, followed by child `net.exe` at `16:14:53.378Z`. Service creation (4697) and scheduled-task creation (4698) around `16:20:07–16:20:09Z` preserve the expected service and Task Scheduler field structures.

- **RDP transport-to-session ordering is convincing.** One transaction begins in `WS-MCHEN-01.meridianhcs.local/ecar.json` at `2024-03-18T16:21:25.676Z` with source `10.10.1.31:51833` to `10.10.2.27:3389`. `zeek-core/conn.json` observes the tuple at `16:21:25.866792Z` under UID `CP6G6JZSjGbVL2lHp9B`, with service `rdp`, 1,876.682196-second duration, state `SF`, and 5,925 missed bytes. Target eCAR logs the inbound flow at `16:21:26.962Z`, then the login at `16:21:33.130Z`; Security 4624 follows at `16:21:33.1436464Z` with user `marcus.chen`, LogonID `0xd8d109e`, LogonGuid `{c5addf0b-832d-4670-83aa-ae8e3fd5c3ec}`, source port 51833, and LogonType 10.

- **SSH lifecycle evidence has realistic source-specific latency.** For source `10.10.1.31:54838` to `FILE-LNX-01:22`, Zeek starts UID `CHdzQQRkGH6sCyBbnJ` at `14:51:01.140903Z`; source eCAR records `ssh.exe` at `14:51:02.082Z`; target eCAR records inbound `sshd` flow at `14:51:04.167Z`; syslog records password acceptance at `14:51:12.279667Z` and PAM open at `14:51:12.442555Z`; and eCAR emits LOGIN at `14:51:13.860Z`. Syslog closes the session at `15:23:02.945422Z`, followed by eCAR LOGOUT at `15:23:04.390Z`. The tuple, user, PID 2711481, and lifecycle order remain coherent without requiring identical timestamps.

- **Zeek contracts and sensor behavior are strong.** `zeek-core` contains 11,102 conn, 2,851 DNS, 1,649 HTTP, 321 SSL, 605 files, 191 X.509, 118 SMB mapping, and 205 SMB file records. Every DNS/HTTP/SSL/SMTP/SMB companion UID exists in the same sensor's conn log; no companion precedes its connection start; and no shared tuple disagrees. All 191 core SSL certificate references resolve to both files and X.509 records; all referenced leaf certificates are valid at observation time and all checked SNI names match SANs. TLS 1.3 uses only TLS 1.3 cipher suites, while TLS 1.2 uses compatible ECDHE suites.

- **Multiple Zeek sensors look independently observed.** Matching core/DMZ connections use different UIDs and a stable approximately 114-ms clock offset. Among 4,103 matched tuples, 3,733 agree on seven principal accounting/state fields while 370 differ in packet/byte/history/missed-byte details. Core/database and DMZ/database pairs show distinct approximately +64-ms and +177-ms skews. Stable sensor clock offsets plus selective accounting differences are more credible than globally copied rows.

- **Text formats preserve native detail.** RFC 5424 syslog priorities align with facilities and severities—for example `<86>` for authpriv informational SSH/PAM records and `<5>` kernel UFW notices. `fw-perimeter/cisco_asa.log` has 6,356 TCP builds versus 6,354 teardowns and 925 UDP builds versus 925 teardowns; the only two unpaired TCP builds are long-lived SSH connections started at 17:32:54 and 17:40:04, close to the window end. HTTP 304 responses use `-` bytes in the web access log and zero body length in Zeek, while CONNECT proxy records separate control-message bytes from tunnel bytes. Bash histories contain 312 parsed timestamp/command pairs, all ordered within each file and with no duplicate timestamp-plus-command pair across files.

## Detailed Analysis
The detailed record sample covered Windows Security 4624, 4625, 4648, 4688, 4697, 4698, 4720, 4728, 4738, 4771, 4800, 4801, 5156, and 1102; Sysmon 1, 3, 5, 7, 8, 10, 11, 13, and 22; eCAR PROCESS, FLOW, MODULE, REGISTRY, FILE, SERVICE, THREAD, and USER_SESSION objects; Zeek conn, DNS, HTTP, SSL, X.509, OCSP, files, SMTP, DHCP, SMB mapping/files, and PE records; and representative syslog, ASA, Snort, web, proxy, and Bash records. Aggregate checks were then used to determine whether sample observations were isolated or systematic.

For Windows field accuracy, `WS-AJOHNSON-01` Security 5156 at `2024-03-18T12:01:46.6470478Z` reports PID 4292, device path `\device\harddiskvolume1\windows\system32\lsass.exe`, outbound direction `%%14593`, `10.10.1.35:65025` to `10.10.2.11:88`, protocol 17, layer `%%14611`, and LayerRTID 48. Its Sysmon 3 counterpart at `12:01:46.7801115Z` reports the same PID, image, tuple, UDP protocol, and `Initiated=true`. eCAR records the same endpoint flow at `12:01:46.668Z`. This is source-native transformation rather than literal row duplication.

Security 4688 and Sysmon 1 process pairs consistently agree on PID, parent PID/image, principal, image, and command line. For the Google updater example, Security record 129955 uses NewProcessId `0x1440` and Sysmon uses decimal PID 5184, both parented by services.exe PID 4284. Sysmon's `UtcTime` has millisecond precision, its envelope has seven fractional digits, Security has seven digits, eCAR uses epoch milliseconds, and Zeek uses six-digit epoch fractions; these source-specific precision choices are correct.

SIDs are stable across the Windows corpus. No username maps to multiple SIDs and no SID maps to multiple principals except the expected alternate DN rendering for `svc_dirsync` in the group-add event. Examples include `marcus.chen` consistently at RID 1003, `aisha.johnson` at RID 1007, and `svc_dirsync` at RID 9101 under the common domain SID base. Logon GUIDs are nonzero for remote interactive sessions and zero where Windows commonly emits an all-zero GUID, while LogonIDs remain hexadecimal and correlate into Sysmon/eCAR process records.

The eCAR files are valid JSON lines, sorted by `timestamp_ms`, and use unique event IDs. Across every host, no event with a resolvable actorID occurs before that actor's visible PROCESS CREATE or after its visible PROCESS TERMINATE. No PROCESS or USER_SESSION object shows a visible terminate/logout preceding a later create/login for the same objectID. Unresolved actorIDs remain present at window boundaries, which is plausible for processes that began before collection.

Zeek packet fields are arithmetically and semantically plausible. Successful DNS rows typically use `Dd`, while TCP services exhibit varied `SF`, `S0`, `RSTO`, `RSTR`, `REJ`, `S1`, `S2`, `S3`, and `OTH` states with corresponding history diversity. ICMP uses type/code in the pseudo-port fields and 28-byte IP-plus-ICMP overhead; DHCP records carry REQUEST/ACK transactions, realistic lease choices, and stable host/MAC assignments. HTTP multi-transaction connections increment `trans_depth`, 304 records omit file bodies, and file FUIds link back to the appropriate connection. Certificate validity, SAN, issuer, OCSP, and cipher checks exposed no contradiction.

The main weakness is not missing source coverage but a small number of source-native realism defects. The 4800/4801 timing is visibly impossible regardless of collection boundaries. The PE-resource placeholders are lower severity but repeat across known binaries and hosts, making them unlikely to be one corrupt event. No comparable hard defect was found in Zeek tuple/UID causality, Windows process/session ordering, eCAR actor lifetimes, ASA connection lifecycles, or SSH/RDP ordering.

- **Temporal patterns:** 8 — Process, session, transport, and sensor order is consistently plausible, but the 406-microsecond lock/unlock pair is a hard outlier.

## Recommendations
1. Enforce a human-plausible dwell time between Security 4800 and 4801 for the same LogonID and SessionId. A lock and unlock should never be emitted at effectively the same instant; preserve the lock state until a later explicit unlock event.

2. Populate Sysmon Event ID 1 PE-resource fields from a stable per-binary identity for installed, hashable executables such as GoogleUpdater.exe, MpCmdRun.exe, Exchange binaries, w3wp.exe, and vendor updaters. If enrichment failure is intentional, vary it according to a defensible collection condition and avoid a repeated pattern in which four hashes always succeed while every version-resource field fails.

3. Retain the current source-specific timestamp precision, Windows provider/task/version mappings, EventRecordID reset semantics, bounded-window lifecycle handling, and transport-before-auth/session ordering. These are the strongest authenticity features.

4. Preserve independent sensor characteristics—distinct Zeek UIDs, stable sensor clock offsets, selective missed bytes, and occasional accounting differences—while continuing to validate that companions do not precede their connection and that certificate/FUID references resolve.

5. Add explicit quality checks for same-session lock/unlock minimum duration and for known PE binaries that repeatedly combine complete hashes with entirely absent version metadata. These checks target the two concrete defects without penalizing valid collection gaps or cross-source completeness.
