## Evidence For Real
- **schema_or_format** — The two `macos_endpoint_security.ndjson` streams have coherent macOS Endpoint Security-shaped records (`schema_version: 1`, `version: 11`) with action results, process/executable metadata, audit tokens, and event-specific fork/exec payloads. For example, on `MAC-MROSS-01`, PID 42171 changes from `/sbin/launchd` to `/usr/libexec/xpcproxy` and then Terminal between `2026-11-02T13:07:43.411700Z` and `.439181Z`; this is a same-process exec-image transition, not a parent/child contradiction.
- **contract_gap** — On that same Mac, PID 42173 / PID version 16 remains `/bin/zsh` while successive fork events produce short-lived children from `13:07:49.995385Z` through `18:14:02.871018Z`; its per-process `seq_num` advances across those events (3, 4, 5 … 50) while global sequence values advance independently. This is internally coherent and avoids the common false alarm of treating each exec image as a new process lifetime.
- **temporal patterns** — Mac shell-history timestamps align with endpoint activity at the relevant granularity: `MAC-MROSS-01` history records `/usr/bin/id` at epoch `1793624869`, matching the Endpoint Security fork/exec of `/usr/bin/id` at `13:07:49.995Z`/`13:07:50.004Z`. The `MAC-MROSS-02` history similarly begins with SSH to `WEB-EXT-01` at `1793624736`, followed by `sw_vers`, `uname`, and `pwd`; its eCAR stream includes a successful local login at `13:04:26.912Z` and host activity continues thereafter.
- **environment_or_collection_plausibility** — Mac-specific records show suitable launchd, loginwindow, Terminal/zsh, application, and sshd roles. `MAC-MROSS-01` Unified Log reports an SSH public-key acceptance at `16:02:15Z`; Endpoint Security shows `sshd-keygen-wrapper` → `sshd` → `sshd-session` process activity beginning at `16:02:13Z`. These are plausible source-native Mac records and timing, without imposing Linux PAM or Windows-only artifacts.
- **temporal patterns** — Windows Sysmon process pairs checked on the domain controllers, file server, mail server, and sampled workstations showed no process termination preceding its matching process creation. Examples include ordinary `winlogon.exe` → `userinit.exe` → `explorer.exe` chains in workstation Sysmon at `13:37:11Z`–`13:37:12Z`, with matching parent ProcessGUIDs. Many processes lack one side of a start/termination pair at the capture boundaries, which is compatible with a six-hour slice.
## Detailed Analysis (specific evidence)
The Windows hosts identify themselves through Security Auditing and Sysmon provider records. The sampled endpoint captures include ordinary user session bootstrap, service activity, common desktop applications, and standard event IDs; process GUIDs and parent GUIDs form credible chains. Security/Sysmon row volume is high on DCs (e.g. DC-01 has 6,947 Security and 4,556 Sysmon events) and much lower on workstations (e.g. WS-SMARTINEZ-01 has 577 Security and 377 Sysmon events). That role-dependent volume is plausible, and completeness alone is not treated as a synthetic tell.

The Mac records support two systems used by `maya.ross`, with local desktop activity and remote SSH activity. Unified Log samples are sparse (three records on MAC-MROSS-01 and two on MAC-MROSS-02), but their contents are consistent with their stated source: loginwindow, kernel Apple System Policy, and sshd-session. The `MeetingAssist.app` policy message at `15:41:59Z` says policy would not allow the process; it does not establish a prompt denial or any child/effects, so I do not infer those. Endpoint Security rows contain both fork and exec records; repeated PID values with increasing PID versions are handled as exec transitions, and parent/responsible audit tokens are not conflated.

The strongest synthetic-looking endpoint evidence is the recurring manual inventory checklist across the two Mac histories. It is not an exact copied file or timestamp sequence: the command order differs, and each file includes distinct SSH targets and repeated subsets. This pattern may reflect repeated troubleshooting or an operator checking multiple systems. Across the examined records I did not identify a definite impossible same-ID event order, a cross-host identity collision, or a lifecycle/value contradiction sufficient to resolve origin.
