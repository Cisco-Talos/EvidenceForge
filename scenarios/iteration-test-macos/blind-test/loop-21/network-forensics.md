# Network Forensics Analyst — Authenticity Assessment

## Verdict
**Mostly synthetic / materially non-production-like.** The bundle contains convincing protocol-level texture and credible multi-sensor web/proxy observations, but a single highly regular internal sweep is a decisive synthetic tell.

## Assessment
The network data is mixed: ordinary DNS, Kerberos, LDAP, SMB, proxy CONNECT, TLS, DHCP, SMTP, and routine failed connection observations have believable byte, duration, and state variation. The large scan event is implausibly exhaustive and mechanically patterned for an otherwise high-volume enterprise trace.

## Verdict Confidence
**High — 0.95.** The finding is directly visible in a complete destination-host/port matrix in Zeek, not inferred from absent companion evidence.

## Synthetic-Confidence Score
**88/100** (lower means more production-like). Score reflects the strong sweep artifact, tempered by realistic ordinary traffic and cross-source observations.

## Executive Summary
At 14:40:24–14:40:52 UTC, `10.10.3.10` contacts all 254 addresses in `10.10.2.0/24` on the same six destination ports, producing 1,521 Zeek connection records: exactly 254 each on ports 0, 443, and 3306, and 253 each on 80, 22, and 445. This is a complete, tightly timed, curated port matrix; most entries are one-packet `S0` attempts, with nine `SF` port-0 rows. The combination of exhaustive host coverage, selected-port symmetry, and port 0 in the same sweep is much more consistent with a generated scan motif than opportunistic production scanning.

Outside that event, the bundle has substantial realistic texture. Zeek records successful and failed flows with varying states, bytes, packet counts, durations, and service labels. DNS query records link to connection records by UID. HTTP CONNECT evidence at the core sensor is complemented by a DMZ-side CONNECT and an external TLS record. DNS activity for randomized `.top` names is varied in timing and response: mostly NXDOMAIN with some sinkhole-like `0.0.0.0` answers. Snort also records selected DNS and SSH scan alerts. Those details make the surrounding traffic more production-like, but do not neutralize the exhaustive sweep.

## Evidence For Synthetic

- **[hard_contradiction] Exhaustive, symmetric subnet/port sweep.** In `zeek-core/conn.json` lines 2500–4035, source `10.10.3.10` generates 1,521 attempts to 254 distinct `10.10.2.x` destinations in about 27 seconds. Port counts are 254 on 0/443/3306 and 253 on 80/22/445. The first records are on lines 2500–2506 (port 0, mostly `S0`); the sequence reaches the final subnet addresses by line 2755 and completes the remaining selected ports by line 4035. The exact /24 coverage and six-port set are unusually complete and regular for production activity.
- **[distribution_texture] Port 0 is embedded in the same all-host matrix.** The 254 port-0 rows are in the initial sweep window (approximately lines 2500–2755); 245 are `S0` with one origin packet and no response, and nine are `SF`. A reserved/invalid destination port appearing once against nearly every host alongside common service ports makes the scan signature conspicuous.
- **[distribution_texture] Highly concentrated attack-shaped activity.** All six port cohorts are generated by one source in the same short window. This compresses what would normally have host/service-specific discovery and follow-up into a single exhaustive matrix.
- **[weak_signal] Deliberately suspicious DNS names.** `zeek-core/dns.json` lines 2489–2951 show 92 `.top` queries from `10.10.3.10`, mainly between 18:00 and 18:45 UTC. Examples include randomized labels on lines 2489, 2496, 2500, and 2951. This is credible as suspicious traffic, but the conspicuous DGA-like naming is an authored behavior and is not by itself a network-format defect.

## Evidence For Real

- **[environment_or_collection_plausibility] Multiple plausible traffic classes and failure states.** `zeek-core/conn.json` contains 11,956 rows with `SF` dominant (9,660), followed by `S0` (1,932), plus lower counts of `RSTO`, `RSTR`, `REJ`, and partial states. It includes ordinary DNS/Kerberos/LDAP/HTTP/SMB/TLS/SMTP/DHCP/SSH/RDP activity rather than only the suspicious motif.
- **[distribution_texture] Byte, packet, and timing variation.** Normal service rows show nonuniform payload and response sizes, durations, and termination states. For example, the LDAP row at core `conn.json` line 434 has a completed exchange with 4,089/32,923 bytes and 6/27 packets, while other LDAP sessions vary and some reset.
- **[contract_gap absent; correlation present] DNS-to-connection identity is internally consistent.** The 92 `.top` DNS events in `zeek-core/dns.json` have matching UIDs in `zeek-core/conn.json` (examples: DNS lines 899, 2489, 2496, 2500 match connection lines 4638, 10122, 10135, 10143). This is positive correlation evidence; no missing pre-window initiator is inferred.
- **[environment_or_collection_plausibility] Realistic proxy and TLS layering.** `zeek-core/http.json` line 1 shows a workstation CONNECT to proxy `10.10.3.20:8080`; `zeek-dmz/http.json` line 1 records the corresponding proxy-side CONNECT, and `zeek-dmz/ssl.json` line 1 records a separate external TLS session with SNI and negotiated TLS 1.3. Sensor-side tuples and UIDs differ as expected for separate observations, so exact cross-sensor UID identity is not required.
- **[distribution_texture] Suspicious DNS has mixed outcomes and varied spacing.** In `zeek-core/dns.json`, 81 of 95 `.top` rows (including one non-`10.10.3.10` query) are NXDOMAIN and 14 are NOERROR; sinkhole-like answers such as `0.0.0.0` have varied TTLs. The 92 queries from `10.10.3.10` span over three hours with irregular inter-arrival times rather than a fixed cadence.
- **[environment_or_collection_plausibility] Independent alert and perimeter sources exist.** `snort-core/snort_alert.log` has 58 records and includes `.top` DNS alerts (line 14) and an SSH scan alert (line 17). `snort-perimeter/snort_alert.log` has external scan alerts, while `fw-perimeter/cisco_asa.log` records inbound builds and teardowns. The perimeter logs are not expected to mirror internal Zeek events, and their differing scope is plausible.

## Detailed Analysis

### Internal scan campaign

The central defect is the Zeek connection matrix at `zeek-core/conn.json` lines 2500–4035. Its first observed timestamp is 2026-11-02 14:40:24.871 UTC and its last is 14:40:52.030 UTC. It covers all 254 usable addresses represented in the `/24`, with essentially the same six-port list on each. The destination-port-0 cohort is concentrated in lines 2500–2755; the first examples (lines 2500–2506) have one origin packet and `S0`, with no response. A sample service-port probe at line 3145 is a reset on TCP/22. This is too complete and too tightly synchronized to resemble normal opportunistic discovery, and the extra port-0 pass amplifies the generated-matrix appearance.

The behavior could represent an intentionally scripted scanner, so the evidence is not that such a scan is impossible. The authenticity issue is the scan's exact breadth and repeated port set across every host in a very short interval, without corresponding unevenness in host selection or service discovery. The finding is classified as a realism contradiction, not a claim that each packet is technically impossible.

### DNS and service traffic

The ordinary network body is much better textured. `zeek-core/conn.json` has a broad protocol/service mix and numerous terminal states. DNS rows commonly have a corresponding `conn.json` UID; this includes the suspicious `.top` events. The query burst has changing labels, responses, and TTLs. The answer behavior (NXDOMAIN or `0.0.0.0`) is plausible for failed and sinkholed lookups; a dependent external connection is not required for those responses.

Proxy observations have a coherent two-hop shape. The core HTTP CONNECT at `zeek-core/http.json` line 1 is from `10.10.1.42` to `10.10.3.20:8080`, while the DMZ HTTP CONNECT at `zeek-dmz/http.json` line 1 and external TLS at `zeek-dmz/ssl.json` line 1 reflect the proxy's egress vantage. The TLS event has a successful handshake, cipher, version, and SNI. This source-native difference is expected and is not treated as a broken UID contract.

Snort records selected suspicious DNS/SSH behavior (`snort-core/snort_alert.log` lines 14 and 17). There is no matching Snort port-sweep alert cited for the 14:40 matrix; that absence is weak evidence only because alert rules and capture/alert coverage are not established by the bundle. Similarly, the perimeter ASA file is scoped to outside/DMZ traffic and is not expected to contain the internal sweep. No missing companion is scored from those omissions.

### Collection scope and bounded window

The assessment treats the available network files as a bounded export. Missing earlier initiators are neutral, and records from different sensor paths are not required to have identical IDs. There is no penalty for thin coverage unless plausible volume/distribution, a required companion, or collection consistency is contradicted. The negative judgment rests on positive evidence: the complete subnet/port matrix visible in Zeek.

## Recommendations

1. Fix the scan-generation root cause so host and port selection follow a bounded, irregular target set rather than a complete `/24 × fixed-port-list` matrix. Keep any intended scan behavior recognizable without identical coverage of every host.
2. Remove destination port 0 from ordinary service-discovery profiles. If an explicit raw probe is a deliberate scenario requirement, model it as a small, purposeful subset rather than a sweep against nearly every host.
3. Preserve the ordinary traffic strengths: protocol-specific state/byte variation, realistic proxy egress layering, DNS/connection UID linkage, varied DGA response outcomes, and sensor-specific observation scope.
4. Do not force Zeek/Snort/firewall rows to correlate one-to-one across collection boundaries. Add alert evidence only where the modeled rule and sensor coverage support it.
